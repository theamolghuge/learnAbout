1. Monolith vs Microservices

MonolithMicroservices
DeploymentOne unit, deployed togetherIndependent services, deployed independently
ScalingScale the whole app, even if only one part is the bottleneckScale only the service that needs it
Tech stackUsually one stack for everythingEach service can pick its own stack/language
Failure isolationA bug can bring down the whole appOne service failing doesn't necessarily take down others (with proper resilience)
ComplexitySimpler operationally — one thing to deploy/monitorNetwork calls, distributed transactions, service discovery, more moving parts
Team structureWorks fine for one teamEnables multiple teams to own/deploy services independently

Interview framing: microservices aren't strictly "better" — they trade simplicity for independent scalability/deployability, and that trade only pays off once a monolith's team size or scaling needs actually justify the added operational complexity. Starting with a monolith and extracting services later is a common, defensible strategy.

2. Service-to-Service Communication

// OpenFeign — declarative HTTP client, looks like calling a local interface
@FeignClient(name = "inventory-service")
public interface InventoryClient {
    @GetMapping("/inventory/{sku}")
    InventoryDto getStock(@PathVariable String sku);
}

@Service
public class OrderService {
    private final InventoryClient inventoryClient;   // injected like any bean

    public void placeOrder(Order order) {
        InventoryDto stock = inventoryClient.getStock(order.getSku());   // looks like a normal method call
        // ... but it's a real HTTP call under the hood, with all the failure modes that implies
    }
}

Feign turns an HTTP call into a plain interface method call — no manual RestTemplate/WebClient boilerplate. But the network is still there: it can time out, the other service can be down, or return an error — which is exactly why resilience patterns (§5) matter for every inter-service call.

3. Service Discovery ⭐

In a dynamic environment (containers restart, autoscaling adds/removes instances), a hardcoded URL like http://10.0.1.5:8080 breaks the moment that instance dies or a new one spins up elsewhere. Service discovery solves this: services register themselves with a central registry on startup, and callers look up "give me a healthy instance of inventory-service" instead of a fixed address.

@EnableEurekaServer   // the registry itself, a separate small Spring Boot app
public class DiscoveryServerApplication { ... }

@EnableDiscoveryClient   // on every microservice — registers itself with Eureka on startup
public class InventoryServiceApplication { ... }

Eureka (Netflix, part of Spring Cloud) is the classic example: each service instance periodically sends a heartbeat; if heartbeats stop, Eureka removes it from the registry, so clients naturally stop being routed to dead instances. Kubernetes has this built in via its own Service/DNS abstraction (see the final topic), which is why many newer stacks skip Eureka entirely when running on k8s.

4. API Gateway

A single entry point that sits in front of all microservices, routing external requests to the right internal service. Consolidates cross-cutting concerns so individual services don't each reimplement them:

ResponsibilityWhy centralize it
RoutingClient calls one host; gateway routes /orders/** to order-service, /users/** to user-service
AuthenticationValidate the JWT once at the edge, not redundantly in every service
Rate limitingProtect all backend services from being overwhelmed, in one place
Request logging/metricsOne place to observe all external traffic

Spring Cloud Gateway is the common Spring-ecosystem choice. Internal service-to-service calls (order-service → inventory-service) typically bypass the gateway entirely and go direct (via service discovery), since the gateway is for external/edge traffic.

5. Circuit Breakers & Resilience ⭐

In a distributed system, a slow or failing downstream service is far more common than in a monolith — every network call can fail. Without protection, one struggling service can cause cascading failures as callers pile up waiting on it, exhausting their own thread pools.

@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackStock")
public InventoryDto getStock(String sku) {
    return inventoryClient.getStock(sku);
}

public InventoryDto fallbackStock(String sku, Throwable t) {
    return InventoryDto.unknown(sku);   // graceful degradation instead of an error/hang
}
StateBehavior
CLOSEDNormal — requests pass through, failures are counted
OPENFailure rate exceeded threshold — requests fail fast immediately (fallback), no call to the struggling service at all, giving it room to recover
HALF_OPENAfter a wait period, lets a few test requests through to see if the service has recovered — closes again if they succeed, re-opens if not

Resilience4j is the modern standard (replacing the now-deprecated Netflix Hystrix), providing circuit breakers, rate limiters, retries, bulkheads, and timeouts as composable annotations/decorators.

6. Distributed Tracing & Centralized Logging

A single user request in a microservices architecture can fan out across many services — debugging "why was this request slow" requires stitching together logs/timing from all of them.

ConceptPurpose
Correlation / trace IDA unique ID generated at the edge (API Gateway) and passed through every downstream call (often via an HTTP header), so all logs for one user request can be grepped together across services
Distributed tracing (e.g. Zipkin, Jaeger)Visualizes the full call graph and timing of a single request across every service it touched — shows exactly which hop was slow
Centralized logging (e.g. ELK stack)Ships every service's logs to one searchable place, instead of SSH-ing into N different machines/pods to piece together what happened

7. Kafka Basics ⭐

Kafka is a distributed, durable, append-only log — producers write messages, consumers read them, and messages persist for a configurable retention period (not deleted once read, unlike a traditional queue).

TermMeaning
TopicA named stream of messages — e.g. "order-placed"
PartitionA topic is split into ordered partitions for parallelism — each partition is an append-only log with sequential offsets. Order is only guaranteed WITHIN a partition, not across the whole topic.
OffsetA message's position within its partition — consumers track which offset they've processed up to
ProducerWrites messages to a topic — chooses (or lets Kafka choose) which partition based on a key
ConsumerReads messages from a topic, tracking its own offset progress
Consumer groupA set of consumers sharing the work of a topic — each partition is consumed by exactly one consumer within a group, enabling parallel processing while each message is still processed once per group

Partition key matters: messages with the same key always land on the same partition (hash of the key), which guarantees ordering for that key — e.g. keying by orderId guarantees all events for one order are processed in order, even though the topic overall is unordered across partitions.

Delivery semantics: Kafka defaults to at-least-once delivery — a consumer might reprocess a message if it crashes after processing but before committing its offset, so consumer logic should be idempotent. Exactly-once semantics are possible with Kafka transactions but add complexity and are used more selectively.

8. Kafka in Spring Boot

@Service
public class OrderEventProducer {
    private final KafkaTemplate kafkaTemplate;

    public void publish(OrderPlacedEvent event) {
        kafkaTemplate.send("order-placed", event.orderId(), event);   // key = orderId
    }
}

@Service
public class InventoryConsumer {
    @KafkaListener(topics = "order-placed", groupId = "inventory-service")
    public void onOrderPlaced(OrderPlacedEvent event) {
        inventoryService.reserve(event.items());   // must be idempotent — could be redelivered
    }
}

spring-kafka wraps the raw Kafka client with Spring-friendly abstractions: KafkaTemplate for producing, @KafkaListener for consuming. The groupId on the listener determines which consumer group it belongs to — running multiple instances of the same service with the same groupId automatically load-balances partitions across them.

9. Async Messaging Patterns

KafkaRabbitMQ
ModelDistributed log — messages retained, can be replayedTraditional message queue/broker — message typically removed once acknowledged
ThroughputVery high — built for high-volume event streamingLower, but very flexible routing (exchanges, routing keys)
OrderingGuaranteed per-partitionGuaranteed per-queue
Use case fitEvent streaming, event sourcing, high-volume analytics pipelines, multiple independent consumers replaying the same eventsTask queues, complex routing, RPC-style request/reply patterns

Why go async at all: synchronous REST calls between services couple their availability — if inventory-service is down, a synchronous call from order-service fails immediately. Publishing an event to Kafka instead decouples them: order-service publishes "order placed" and moves on; inventory-service processes it whenever it's able to, even if it was briefly down when the event was published.
