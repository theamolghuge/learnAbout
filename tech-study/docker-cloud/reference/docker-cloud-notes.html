1. Docker Concepts

TermMeaning
ImageAn immutable, read-only template — filesystem + metadata describing how to run an app. Built once, run many times.
ContainerA running instance of an image — an isolated process with its own filesystem view, network, but sharing the host's kernel (unlike a VM, which virtualizes the whole OS)
LayerEach Dockerfile instruction creates a cached, reusable layer — unchanged layers are reused on rebuild, which is why instruction ORDER in a Dockerfile matters for build speed
RegistryWhere images are stored/versioned (Docker Hub, ECR, GitHub Container Registry) — `docker push`/`docker pull`

Container vs VM: a VM virtualizes hardware and runs a full guest OS per instance (heavy, slow to start, GBs). A container shares the host OS kernel and only isolates the process/filesystem view (lightweight, starts in ~milliseconds, MBs) — this is why you can run dozens of containers on a host that could maybe run a handful of VMs.

2. Dockerfile for Spring Boot ⭐

# Multi-stage build — stage 1 builds the jar, stage 2 only ships the runtime
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

FROM eclipse-temurin:21-jre AS runtime
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Why multi-stage: the build stage needs the full JDK + Maven + source code (large). The final runtime image only needs the JRE (smaller, no compiler) and the built jar — copying just the artifact out of the build stage keeps the shipped image small and avoids bundling build tools, source code, and caches that add attack surface and size with zero runtime benefit.

docker build -t order-service:1.0 .
docker run -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod order-service:1.0

Layer caching tip: copying pom.xml and running the dependency download before copying the rest of the source lets Docker reuse the cached dependency layer on rebuilds where only application code changed, not dependencies — significantly speeding up iterative builds.

3. Docker Compose

Compose defines and runs multi-container applications from one YAML file — the standard way to spin up your app plus its dependencies (database, cache) together for local development.

# docker-compose.yml
services:
  app:
    build: .
    ports: ["8080:8080"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/mydb
    depends_on: [db]

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: mydb
      POSTGRES_PASSWORD: secret
    volumes: ["pgdata:/var/lib/postgresql/data"]

volumes:
  pgdata:

docker compose up starts everything together, on a shared network where services can reach each other by service name (e.g. db resolves to the Postgres container's IP) — no manual network wiring. volumes persist data (like the database) across container restarts.

4. CI/CD Pipeline ⭐

git push
  → CI triggers automatically
  → Checkout code → mvn clean test (unit + integration tests)
  → mvn package (build the jar)
  → docker build (containerize) → docker push (to a registry)
  → CD: deploy the new image to staging/production
# .github/workflows/ci.yml — GitHub Actions
name: CI
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }
      - run: mvn clean verify
      - run: docker build -t myapp:${{ github.sha }} .
Continuous IntegrationContinuous Deployment/Delivery
GoalEvery push is automatically built + tested — catch integration bugs immediatelyEvery change that passes CI is automatically (or with one click) released
Failure mode it prevents"Works on my machine" / broken main branchSlow, risky, manual release process

Continuous Delivery (manual approval to release) vs Continuous Deployment (fully automatic release, no human gate) is a common point of confusion — Delivery means it's always releasable; Deployment means it actually auto-releases.

5. AWS Basics

ServiceWhat it's for
EC2Virtual machines — rent compute by the hour, run anything including a Spring Boot jar or Docker container directly
S3Object storage — files/blobs (images, backups, logs), not a database; durable, cheap, virtually unlimited
RDSManaged relational database (Postgres/MySQL/etc.) — AWS handles backups, patching, failover, so you don't run your own DB server
IAMIdentity and Access Management — who (users, services) can do what (permissions) on which resources; the backbone of AWS security
CloudWatchMetrics, logs, and alarms — where your app's logs go, and what pages someone when error rates spike
VPCVirtual Private Cloud — an isolated network you control (subnets, routing, firewall rules) that your resources live inside
Load Balancer (ELB/ALB)Distributes incoming traffic across multiple app instances — enables horizontal scaling and zero-downtime deploys

How these fit together for a typical Spring Boot deployment: a Load Balancer sits in front of multiple EC2 instances (or containers) running the app, inside a VPC; the app connects to an RDS database; IAM roles grant the app instances only the specific permissions they need (least privilege); CloudWatch collects logs and metrics from everything.

6. Deployment Models

StrategyHow it worksTrade-off
RollingReplace old instances with new ones a few at a timeNo downtime, but old and new versions run simultaneously during rollout — requires backward-compatible changes
Blue-greenDeploy the new version fully alongside the old, then switch traffic all at onceInstant rollback (switch back), but needs double the infrastructure briefly
CanaryRoute a small % of traffic to the new version first, then ramp upLimits blast radius of a bad deploy, but needs good monitoring to catch issues early
