Joins

What's the difference between INNER JOIN and LEFT JOIN?

INNER JOIN returns only rows that have a match in both tables. LEFT JOIN returns every row from the left table regardless of a match, filling right-side columns with NULL when there's no matching row. Use LEFT JOIN when you need "all of A, with B's data if it exists" — e.g. all customers including ones with zero orders.

How would you find customers who have never placed an order?

LEFT JOIN customers to orders, then filter WHERE the order's id IS NULL — rows with no match on the right side have NULL there. Equivalently, WHERE customer_id NOT IN (SELECT customer_id FROM orders), though NOT IN has NULL-handling pitfalls that make the LEFT JOIN or NOT EXISTS versions safer.

What is a self join and when would you use one?

Joining a table to itself, using two aliases, to compare rows within the same table — e.g. finding employees who earn more than their own manager by joining the employees table to itself on manager_id = id.

Aggregates & Grouping

Why can't you filter on an aggregate in WHERE?

Because of SQL's logical evaluation order: WHERE runs before GROUP BY, so the aggregated values don't exist yet at that point. HAVING runs after grouping/aggregation, which is why it's the clause used to filter on things like COUNT(*) or SUM(total).

Difference between COUNT(*) and COUNT(column)?

COUNT(*) counts every row regardless of NULLs. COUNT(column) counts only rows where that specific column is non-null — useful for counting how many rows actually have a value set for an optional field.

Keys & Constraints

What's the difference between a primary key and a unique constraint?

A table can have only one primary key, and it can't be NULL — it's the canonical row identifier, and it's typically what foreign keys reference. A table can have multiple unique constraints, and depending on the database, a unique column may allow one or more NULLs (NULLs generally aren't considered equal to each other).

What does ON DELETE CASCADE do, and when is it dangerous?

It automatically deletes child rows when the referenced parent row is deleted — e.g. deleting a customer deletes all their orders. It's dangerous when the cascade chain is long or unintentional — a single delete can silently wipe out data several tables deep. ON DELETE RESTRICT (block the delete if children exist) is the safer default unless cascading is explicitly the desired business behavior.

Indexes

What is a database index, and what's the trade-off of adding one?

A separate B-tree structure over one or more columns that lets the database jump directly to matching rows instead of scanning the whole table — turning an O(n) scan into roughly O(log n) lookup. The cost: every INSERT/UPDATE/DELETE must also update the index, so writes get slower and the index consumes extra disk space. Index columns used heavily in WHERE/JOIN/ORDER BY; don't index everything.

You have a composite index on (customer_id, status). Does a query filtering only on status use it?

Generally no — composite indexes follow the leftmost-prefix rule. The index is usable when the query filters on customer_id alone, or on customer_id AND status together, but not when it filters on status alone, since the index is physically sorted by customer_id first.

Transactions

Explain ACID.

Atomicity — all statements in a transaction succeed or none do. Consistency — the database moves between valid states, constraints always hold. Isolation — concurrent transactions don't observe each other's uncommitted changes. Durability — once committed, the change survives a crash.

What's the difference between a dirty read, a non-repeatable read, and a phantom read?

Dirty read: seeing another transaction's uncommitted changes. Non-repeatable read: re-reading the same row within one transaction and getting a different value because another transaction committed a change in between. Phantom read: re-running the same filtered query and getting different rows because another transaction inserted/deleted matching rows in between. Higher isolation levels progressively eliminate these, at the cost of concurrency.

What isolation level does Spring's @Transactional use by default?

By default it doesn't override anything — it uses whatever the underlying database's default isolation level is (READ COMMITTED for Postgres, REPEATABLE READ for MySQL/InnoDB). You can override it explicitly with @Transactional(isolation = Isolation.SERIALIZABLE) when a specific operation needs stronger guarantees.

Normalization

Why would you deliberately denormalize a schema?

To trade write-time consistency for read-time performance — e.g. storing a precomputed order total or a cached customer name to avoid an expensive join or aggregation on every read. It's a deliberate, measured trade-off, not a default; it introduces the risk of the duplicated data drifting out of sync if updates aren't kept consistent.

JDBC

Why is PreparedStatement preferred over Statement?

Two reasons: security — PreparedStatement sends parameters separately from the SQL text, so user input can never be interpreted as SQL syntax, preventing SQL injection; Statement requires string concatenation, which is exploitable. Performance — a PreparedStatement's query plan can be precompiled and reused across executions with different parameter values.

Why do we pool database connections instead of opening a new one per request?

Opening a connection involves a TCP handshake and authentication — tens of milliseconds, far too slow to repeat on every request under load. A pool (e.g. HikariCP, Spring Boot's default) keeps a set of connections open and hands them out on demand, dramatically reducing per-request latency and avoiding overwhelming the database with connection churn.

What does try-with-resources buy you specifically with JDBC objects?

Connection, Statement, and ResultSet all implement AutoCloseable — wrapping them in try-with-resources guarantees they're closed (and, for Connection, returned to the pool) even if an exception is thrown mid-query, preventing connection leaks that would eventually exhaust the pool.
