1. SQL Basics

SELECT id, name, email
FROM users
WHERE created_at > '2026-01-01'
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;          -- pagination: page 3, 20 per page

INSERT INTO users (name, email) VALUES ('Ada', 'ada@example.com');

UPDATE users SET email = 'new@example.com' WHERE id = 10;

DELETE FROM users WHERE id = 10;

Clause evaluation order differs from write order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This is why you can't reference a SELECT alias in the same query's WHERE clause — WHERE runs before SELECT.

2. Joins ⭐

JoinReturns
INNER JOINOnly rows with a match in both tables
LEFT JOINAll rows from the left table, matched columns from the right (NULL if no match)
RIGHT JOINAll rows from the right table, matched columns from the left (NULL if no match) — rarely used, a LEFT JOIN with tables swapped is equivalent and more common in practice
FULL OUTER JOINAll rows from both sides, NULLs where no match — not supported by MySQL directly
-- Every order with its customer name — orders with a deleted customer are dropped
SELECT o.id, c.name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.id;

-- Every customer, even ones with zero orders (order columns are NULL)
SELECT c.name, o.id AS order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;

-- Find customers with NO orders — the classic LEFT JOIN + IS NULL pattern
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

Self join: join a table to itself to compare rows within it — e.g. finding employees who earn more than their manager, by joining employees e1 to employees e2 on e1.manager_id = e2.id.

3. Aggregate Functions & Grouping

FunctionDoes
COUNT(*) / COUNT(col)Row count / non-null value count
SUM, AVG, MIN, MAXNumeric aggregation
-- Orders per customer, only customers with more than 5 orders
SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 5
ORDER BY order_count DESC;

WHERE vs HAVING: WHERE filters raw rows before grouping; HAVING filters groups after aggregation. You can't put an aggregate function in WHERE — the aggregate doesn't exist yet at that stage of evaluation.

4. Subqueries

-- Scalar subquery — customers who spent more than the average order
SELECT * FROM orders WHERE total > (SELECT AVG(total) FROM orders);

-- IN — customers who have placed at least one order
SELECT * FROM customers WHERE id IN (SELECT customer_id FROM orders);

-- Correlated subquery — re-evaluated per outer row, references the outer table
SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

EXISTS vs IN: EXISTS stops at the first match (short-circuits) and handles NULLs safely — generally preferred for large subquery result sets. IN materializes the full subquery result first and can behave unexpectedly if that list contains NULL.

5. Keys & Constraints

ConstraintEnforces
PRIMARY KEYUnique + not null identifier for each row — one per table, often auto-incrementing
FOREIGN KEYA column must reference an existing row in another table — maintains referential integrity
UNIQUENo duplicate values in the column, but NULL is allowed (implementation-dependent)
NOT NULLColumn must always have a value
CHECKCustom boolean condition, e.g. CHECK (price >= 0)
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id),
    total NUMERIC(10,2) CHECK (total >= 0),
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
);

A foreign key delete behavior matters in interviews: ON DELETE CASCADE (delete children too), ON DELETE RESTRICT (block the delete if children exist — the safe default), ON DELETE SET NULL.

6. Indexes ⭐

An index is a separate data structure (usually a B-tree) that lets the database find rows without scanning the whole table — the equivalent of a book's index instead of reading every page.

CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- Composite index — column order matters, leftmost-prefix rule
CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
-- Usable for: WHERE customer_id = ?  AND  WHERE customer_id = ? AND status = ?
-- NOT usable for: WHERE status = ? alone
BenefitCost
Fast lookups on WHERE/JOIN/ORDER BY columns — O(log n) vs O(n) full scanSlower writes — every INSERT/UPDATE/DELETE must also update the index
Extra disk space — each index is a full copy of the indexed columns plus pointers

Rule of thumb: index foreign keys and columns frequently used in WHERE/JOIN/ORDER BY; don't index every column, and don't index low-cardinality columns (e.g. a boolean) alone — the database often skips the index and scans anyway.

7. Transactions & ACID ⭐

LetterGuarantee
AtomicityAll statements in the transaction succeed, or none do (rollback)
ConsistencyA transaction moves the DB from one valid state to another — constraints always hold
IsolationConcurrent transactions don't see each other's uncommitted changes
DurabilityOnce committed, the change survives a crash
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- both succeed together, or ROLLBACK undoes both

Isolation levels — the trade-off knob

LevelPreventsAllows
READ UNCOMMITTEDNothingDirty reads (see uncommitted changes)
READ COMMITTED (Postgres default)Dirty readsNon-repeatable reads (same row changes between reads in one tx)
REPEATABLE READ (MySQL default)Dirty + non-repeatable readsPhantom reads (new rows matching a filter appear)
SERIALIZABLEAll of the aboveNothing — behaves as if transactions ran one at a time; lowest concurrency

This is what Spring's @Transactional(isolation = ...) configures. Higher isolation = safer but more locking/lower throughput.

8. Normalization

FormRule
1NFAtomic columns — no repeating groups or arrays crammed into one column
2NF1NF + every non-key column depends on the whole primary key (matters for composite keys)
3NF2NF + no non-key column depends on another non-key column (no transitive dependency)

Example violation: storing customer_name directly on the orders table instead of just customer_id — it's transitively dependent on the customer, not the order, and will drift out of sync if the customer renames. Normalize to remove duplication; deliberately denormalize (e.g. cache a computed total) only for measured read-performance wins, and know you're trading consistency risk for speed when you do.

9. JDBC ⭐

JDBC is the low-level API Java uses to talk to a relational database. Spring Data JPA/Hibernate use JDBC underneath — understanding this layer explains what's actually happening when a repository method runs.

String url = "jdbc:postgresql://localhost:5432/mydb";
try (Connection conn = DriverManager.getConnection(url, user, password);
     PreparedStatement stmt = conn.prepareStatement(
         "SELECT id, name FROM users WHERE email = ?")) {

    stmt.setString(1, "ada@example.com");
    try (ResultSet rs = stmt.executeQuery()) {
        while (rs.next()) {
            long id = rs.getLong("id");
            String name = rs.getString("name");
        }
    }
}
TypePurpose
ConnectionA live session to the database — expensive to open, hence pooling (§10)
StatementRuns a static SQL string — vulnerable to SQL injection if you concatenate user input into it
PreparedStatementPrecompiled SQL with ? placeholders — parameters are sent separately from the query, so user input can never be interpreted as SQL. Also faster for repeated execution.
ResultSetA cursor over the query results — read forward with .next(), closed automatically by try-with-resources
// NEVER do this — string concatenation enables SQL injection
String sql = "SELECT * FROM users WHERE email = '" + userInput + "'";
// userInput = "' OR '1'='1" returns every row

// ALWAYS do this — the driver treats the parameter as pure data, never as SQL
PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE email = ?");
stmt.setString(1, userInput);

10. Connection Pooling

Opening a DB connection (TCP handshake + auth) takes tens of milliseconds — far too slow to do per request. A connection pool keeps a set of open connections ready to reuse: borrow one, use it, return it to the pool instead of closing it.

# application.yml — HikariCP is Spring Boot's default pool
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 30000   # ms to wait for a free connection before failing

HikariCP is the fastest and default pool in Spring Boot. Sizing rule of thumb: pool size should relate to available DB connections and typical query concurrency, not just "bigger is better" — an oversized pool can overwhelm the database with concurrent queries and actually reduce throughput.
