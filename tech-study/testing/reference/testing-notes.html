1. The Test Pyramid

        /\
       /  \    E2E / UI tests        — few, slow, brittle, highest confidence
      /----\
     /      \  Integration tests     — some, medium speed (@SpringBootTest, @WebMvcTest)
    /--------\
   /          \ Unit tests           — many, fast, isolated (plain JUnit + Mockito)
  /------------\

Most tests should be fast unit tests with no Spring context at all — a plain new ServiceUnderTest(mockDependency) runs in milliseconds. Spring context tests are slower (starting a context takes real time) so they're used more sparingly, targeted at the specific layer being verified.

2. JUnit 5 ⭐

class OrderCalculatorTest {

    private OrderCalculator calculator;

    @BeforeEach                          // runs before every test method
    void setUp() {
        calculator = new OrderCalculator();
    }

    @Test
    void calculatesTotalWithTax() {
        double total = calculator.totalWithTax(100.0, 0.08);
        assertEquals(108.0, total, 0.001);      // delta for double comparison
    }

    @Test
    void throwsOnNegativePrice() {
        assertThrows(IllegalArgumentException.class,
            () -> calculator.totalWithTax(-10.0, 0.08));
    }

    @ParameterizedTest
    @ValueSource(doubles = {0.0, 0.05, 0.2})
    void handlesVariousTaxRates(double rate) {
        assertTrue(calculator.totalWithTax(100.0, rate) >= 100.0);
    }

    @AfterEach
    void tearDown() { /* cleanup, e.g. close resources */ }
}
AnnotationPurpose
@TestMarks a test method
@BeforeEach / @AfterEachRuns before/after every test in the class — fresh state per test
@BeforeAll / @AfterAllRuns once for the whole class — must be static
@ParameterizedTestRuns the same test body across multiple input sets — avoids copy-pasted near-duplicate tests
@DisplayNameHuman-readable test name in reports

assertEquals vs assertThrows vs assertTrue — the common assertion set. Prefer assertThrows over a manual try/catch that fails the test if no exception is thrown; it's clearer and idiomatic.

3. Mockito ⭐

A mock is a fake implementation of a dependency whose behavior you control, so you can test a unit in isolation without its real collaborators (database, network, other services).

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;      // fake — no real DB

    @Mock
    private PaymentClient paymentClient;

    @InjectMocks
    private OrderService orderService;             // real object, mocks injected via constructor

    @Test
    void placeOrder_savesAndCharges() {
        Order order = new Order("Ada", 100.0);
        when(orderRepository.save(any(Order.class))).thenReturn(order);   // stub behavior

        orderService.placeOrder(order);

        verify(paymentClient).charge(order.getTotal());   // behavior verification — was it called?
        verify(orderRepository, times(1)).save(order);
    }

    @Test
    void placeOrder_whenRepositoryFails_doesNotCharge() {
        when(orderRepository.save(any())).thenThrow(new DataAccessException("db down") {});

        assertThrows(DataAccessException.class, () -> orderService.placeOrder(new Order("Ada", 100.0)));
        verifyNoInteractions(paymentClient);   // charge should never be reached
    }
}
ConceptMeaning
@MockCreates a fake with all methods stubbed to return null/0/false by default
@InjectMocksCreates the real class under test, injecting the @Mock fields (via constructor if available)
when(...).thenReturn(...)Stub a mock's return value for a given call
verify(mock).method(...)Assert a method WAS called — behavior verification, distinct from checking a return value
@SpyWraps a REAL object — calls go to the real method unless explicitly stubbed. Rarely needed; usually a sign to redesign.

Mock vs stub vs spy, informally: a stub just returns canned data when asked; a mock additionally lets you verify it was called correctly; a spy wraps a real object and lets you selectively override some methods while keeping real behavior for others.

4. Unit Testing a Service Layer

The service layer is the sweet spot for pure unit tests: mock the repository (and any other collaborators), instantiate the service directly with new or @InjectMocks — no Spring context needed at all, so these tests run in milliseconds and don't need a database.

class UserServiceTest {
    @Mock private UserRepository repository;
    @InjectMocks private UserService service;

    @Test
    void findById_throwsWhenMissing() {
        when(repository.findById(1L)).thenReturn(Optional.empty());
        assertThrows(UserNotFoundException.class, () -> service.findById(1L));
    }
}

5. @WebMvcTest — Testing Controllers

@WebMvcTest loads only the web layer (controllers, filters, @ControllerAdvice) — not the full application context, not real repositories/database. Any service the controller depends on must be mocked (typically with @MockBean).

@WebMvcTest(UserController.class)
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean                              // registers a Mockito mock into the Spring context
    private UserService userService;

    @Test
    void getUser_returns200AndBody() throws Exception {
        when(userService.findById(1L)).thenReturn(new UserDto(1L, "Ada"));

        mockMvc.perform(get("/users/1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("Ada"));
    }

    @Test
    void createUser_withInvalidBody_returns400() throws Exception {
        mockMvc.perform(post("/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"email\":\"not-an-email\"}"))
            .andExpect(status().isBadRequest());
    }
}

MockMvc simulates HTTP requests against the controller without starting a real servlet container/port — fast, but still exercises the real request-mapping, validation, and JSON serialization logic. This is the right layer to verify status codes, response shapes, and validation error handling.

6. @DataJpaTest — Testing Repositories

@DataJpaTest loads only the JPA-related slice of the context (entities, repositories, an EntityManager) against an in-memory embedded database (H2 by default) — and wraps each test in a transaction that's rolled back afterward, so tests never pollute each other.

@DataJpaTest
class UserRepositoryTest {

    @Autowired
    private UserRepository userRepository;

    @Test
    void findByEmail_returnsMatchingUser() {
        userRepository.save(new User("ada@example.com"));

        Optional found = userRepository.findByEmail("ada@example.com");

        assertTrue(found.isPresent());
    }
}

Good for verifying custom @Query/derived query methods actually do what you expect — logic Mockito can't test, since there's no real query execution to mock.

7. @SpringBootTest — Full Integration Tests

@SpringBootTest boots the entire application context — every bean, real or close-to-real. It's the slowest and heaviest test type, so it's used sparingly, for a handful of true end-to-end flows rather than every scenario.

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
class OrderFlowIntegrationTest {

    @Autowired private MockMvc mockMvc;
    @Autowired private OrderRepository orderRepository;

    @Test
    void placingAnOrder_persistsItToTheDatabase() throws Exception {
        mockMvc.perform(post("/orders").contentType(MediaType.APPLICATION_JSON)
                .content("{\"item\":\"Book\",\"quantity\":2}"))
            .andExpect(status().isCreated());

        assertEquals(1, orderRepository.count());   // verifies real end-to-end persistence
    }
}
Test typeLoadsSpeedUse for
Plain unit testNothing — just the class under test + MockitoFastestService/business logic — the bulk of your tests
@WebMvcTestWeb layer onlyFastControllers — status codes, request/response shape, validation
@DataJpaTestJPA layer + embedded DBMediumRepositories — custom queries actually work
@SpringBootTestFull application contextSlowestA few critical end-to-end flows

8. Testcontainers

H2 (an in-memory DB) is fast but isn't the real database — SQL dialect differences can hide bugs that only show up against real Postgres/MySQL in production. Testcontainers spins up a real database (or Kafka, Redis, etc.) in a throwaway Docker container for the duration of the test run, giving high-fidelity integration tests without a shared, stateful test environment.

@Testcontainers
@SpringBootTest
class OrderRepositoryIT {

    @Container
    static PostgreSQLContainer postgres = new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void configure(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
    }
}
