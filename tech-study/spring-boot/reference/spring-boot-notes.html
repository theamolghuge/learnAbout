1. IoC & Dependency Injection ⭐

Inversion of Control: instead of your code creating and wiring its own dependencies (new UserService(new UserRepository())), you hand that responsibility to a container. The container ("Spring context") creates objects and wires them together based on configuration/annotations — control over object creation is inverted from your code to the framework.

Dependency Injection is the mechanism IoC uses: the container "injects" a class's dependencies into it, rather than the class constructing them itself.

Constructor vs field vs setter injection

// Constructor injection — preferred
@Service
public class OrderService {
    private final OrderRepository repository;   // can be final — immutable
    private final PaymentClient paymentClient;

    public OrderService(OrderRepository repository, PaymentClient paymentClient) {
        this.repository = repository;
        this.paymentClient = paymentClient;
    }
}

// Field injection — avoid in real code
@Service
public class OrderService {
    @Autowired
    private OrderRepository repository;   // can't be final, hides dependencies, hard to test
}

Why constructor injection wins: dependencies are explicit in the signature (easy to see what a class needs), fields can be final (immutable, fail-fast if a dependency is missing), and it's trivial to unit test — just call new OrderService(mockRepo, mockClient) with no Spring context needed. With a single constructor, @Autowired is even optional — Spring infers it.

2. Beans, Component Scanning & Configuration

A bean is any object managed by the Spring container — created, configured, and wired by Spring instead of by your own code.

AnnotationMarks
@ComponentGeneric Spring-managed bean
@ServiceBusiness logic layer — semantically a @Component, signals intent
@RepositoryData access layer — a @Component that also translates DB exceptions into Spring's unchecked DataAccessException hierarchy
@Controller / @RestControllerWeb layer — handles HTTP requests. @RestController = @Controller + @ResponseBody on every method

Component scanning: Spring Boot's @SpringBootApplication includes @ComponentScan, which walks the package it's in (and sub-packages) looking for these stereotype annotations and registers each as a bean automatically.

@Configuration
public class AppConfig {
    @Bean
    public RestTemplate restTemplate() {          // manual bean definition —
        return new RestTemplate();                 // for 3rd-party classes you can't annotate
    }
}

3. Bean Lifecycle & Scopes

Lifecycle (high level)

Instantiate → Populate properties (DI) → @PostConstruct / InitializingBean
  → bean ready for use →  (container shutdown) → @PreDestroy / DisposableBean
@Service
public class CacheWarmer {
    @PostConstruct
    void warmUp() { /* runs once, right after DI is complete */ }

    @PreDestroy
    void cleanup() { /* runs on graceful shutdown */ }
}

Bean scopes

ScopeMeaning
singleton (default)One shared instance per Spring container — this is why beans should generally be stateless
prototypeA new instance every time the bean is requested/injected
requestOne instance per HTTP request (web apps only)
sessionOne instance per HTTP session (web apps only)

Interview trap: since the default is singleton, never store per-request mutable state in a plain instance field of a @Service/@Controller — every request shares that same object, so it's a concurrency bug waiting to happen. Pass state through method parameters instead.

4. Spring Boot Basics

Spring Boot is opinionated Spring — it doesn't replace the Spring Framework, it removes the boilerplate of configuring it. Three big pieces:

FeatureWhat it does
StartersCurated dependency bundles — spring-boot-starter-web pulls in Spring MVC, Jackson, and an embedded Tomcat with compatible versions, so you don't hand-pick each jar
Auto-configurationInspects what's on the classpath and configures beans accordingly — e.g. seeing a DataSource + JPA on the classpath auto-configures an EntityManagerFactory. Backed off automatically if you define your own bean of that type.
Embedded serverTomcat (default), Jetty, or Undertow is bundled inside the fat jar — java -jar app.jar starts a running web server, no external app server / WAR deployment needed
@SpringBootApplication   // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

pom.xml (Maven) declares dependencies via starters and uses the spring-boot-maven-plugin to produce an executable "fat jar" containing all dependencies.

5. Configuration & Profiles

# application.yml
spring:
  application:
    name: order-service
server:
  port: 8080
app:
  payment-timeout-ms: 3000

---
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 80
@Component
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private int paymentTimeoutMs;   // bound from app.payment-timeout-ms
    // getters/setters
}

@Value("${app.payment-timeout-ms}")   // simpler, single-value alternative
private int timeout;

Profiles (dev, test, prod) let you swap configuration per environment — activate with -Dspring.profiles.active=prod or the SPRING_PROFILES_ACTIVE env var. Properties resolve with a defined precedence: command-line args > env vars > profile-specific YAML > base application.yml, so ops can override any setting without touching the jar.

6. Spring Boot Actuator

Actuator exposes production-ready operational endpoints out of the box — add spring-boot-starter-actuator and get:

EndpointShows
/actuator/healthUP/DOWN status, including downstream checks (DB, disk space) — what load balancers/Kubernetes probe
/actuator/metricsJVM memory, GC pauses, HTTP request timings, custom app metrics
/actuator/infoBuild/version metadata you configure
/actuator/envResolved configuration properties (sensitive — lock this down in prod)

Only health and info are exposed over HTTP by default; the rest must be explicitly enabled and are typically restricted to an internal network in production.

7. HTTP Fundamentals

MethodPurposeIdempotent?Safe (no side effects)?
GETReadYesYes
POSTCreate / non-idempotent actionNoNo
PUTFull replace (create-or-replace)YesNo
PATCHPartial updateNo (by spec, though often implemented idempotently)No
DELETERemoveYesNo

Idempotent means calling it once vs. many times with the same input leaves the system in the same state — important for safe retries over an unreliable network.

StatusMeaning
200 OKSuccess, response body present
201 CreatedResource created — pair with a Location header
204 No ContentSuccess, no body (common for DELETE)
400 Bad RequestMalformed/invalid client input
401 UnauthorizedNot authenticated
403 ForbiddenAuthenticated but not permitted
404 Not FoundResource doesn't exist
409 ConflictRequest conflicts with current state (e.g. duplicate unique field)
422 Unprocessable EntityWell-formed but semantically invalid (failed validation)
500 Internal Server ErrorUnhandled server-side failure

8. Building REST APIs ⭐

@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping                          // GET /users
    public List getAll() {
        return userService.findAll();
    }

    @GetMapping("/{id}")                 // GET /users/10
    public UserDto getOne(@PathVariable Long id) {
        return userService.findById(id);
    }

    @GetMapping(params = "role")         // GET /users?role=admin
    public List getByRole(@RequestParam String role) {
        return userService.findByRole(role);
    }

    @PostMapping                         // POST /users
    @ResponseStatus(HttpStatus.CREATED)
    public UserDto create(@RequestBody @Valid CreateUserRequest request) {
        return userService.create(request);
    }

    @PutMapping("/{id}")                 // PUT /users/10
    public UserDto update(@PathVariable Long id, @RequestBody @Valid UpdateUserRequest request) {
        return userService.update(id, request);
    }

    @DeleteMapping("/{id}")              // DELETE /users/10
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        userService.delete(id);
    }
}
AnnotationBinds
@PathVariableA segment of the URL path, e.g. the 10 in /users/10
@RequestParamA query string parameter, e.g. ?role=admin — supports defaults/optional
@RequestBodyDeserializes the JSON request body into a Java object via Jackson
@ResponseStatusOverrides the default 200 status code for a handler

Jackson (bundled by spring-boot-starter-web) handles JSON ⇄ Java conversion automatically for @RequestBody/return values — this is why a plain POJO returned from a @RestController method just becomes a JSON response with no manual serialization code.

9. Request Lifecycle — What Actually Happens

HTTP request
  → Embedded Tomcat accepts the connection, hands it to the servlet container
  → DispatcherServlet (Spring MVC's front controller) receives it
  → HandlerMapping finds the matching @RequestMapping method
  → Filters/Interceptors run (auth, logging, CORS)
  → Method invoked — @RequestBody deserialized, @Valid runs validation
  → Controller calls Service → Repository → database
  → Return value serialized to JSON (Jackson) via HttpMessageConverter
  → Response sent back through the same filter chain

Every incoming request is handled on its own thread from Tomcat's pool (default max 200) — this is why singleton beans should be stateless: many request threads call the same controller/service instance concurrently.
