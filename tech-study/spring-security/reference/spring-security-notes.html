1. Authentication vs Authorization

Question it answersFailure status
Authentication (AuthN)Who are you? — verifying identity (login)401 Unauthorized
Authorization (AuthZ)What are you allowed to do? — checking permissions403 Forbidden

Authentication always happens first — you can't check permissions for an unknown identity. In Spring Security, authentication populates a SecurityContext with an Authentication object (principal + granted authorities); authorization decisions (@PreAuthorize, URL rules) then read from that context.

2. The Security Filter Chain ⭐

Spring Security works by inserting a chain of servlet filters in front of your controllers — every request passes through this chain before it ever reaches a @RestController.

Request → CorsFilter → CsrfFilter → (Custom) JwtAuthFilter
        → UsernamePasswordAuthenticationFilter → ExceptionTranslationFilter
        → FilterSecurityInterceptor (authorization check)
        → DispatcherServlet → your @RestController
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                       // stateless JWT APIs don't need CSRF protection
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/register", "/auth/login").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

This SecurityFilterChain bean approach is the current (Spring Security 5.7+) way to configure security — it replaced the older WebSecurityConfigurerAdapter subclassing style, which is deprecated.

3. Password Hashing

Passwords must never be stored in plaintext or with a fast general-purpose hash like MD5/SHA-256 — those are designed to be fast, which makes brute-forcing leaked hashes cheap. Use a slow, salted algorithm designed for passwords.

@Autowired
private PasswordEncoder passwordEncoder;   // BCryptPasswordEncoder

String hashed = passwordEncoder.encode(rawPassword);   // includes a random salt automatically
boolean matches = passwordEncoder.matches(rawPassword, hashed);   // used at login

BCrypt is the Spring Security default — it's deliberately slow (configurable "work factor"/cost) and automatically salts each hash, so two users with the same password get different hashes, and brute-forcing requires redoing the expensive computation per guess.

4. Roles & Permissions

@RestController
public class AdminController {

    @PreAuthorize("hasRole('ADMIN')")
    @GetMapping("/admin/reports")
    public List reports() { ... }

    @PreAuthorize("hasAuthority('REPORTS_READ')")   // finer-grained than a role
    @GetMapping("/reports")
    public List myReports() { ... }
}

Role vs authority: a "role" is really just an authority with a ROLE_ prefix by convention (hasRole("ADMIN") checks for authority ROLE_ADMIN). Authorities are the more general, granular building block — a role is typically a bundle of authorities (e.g. ROLE_ADMIN implies REPORTS_READ, USERS_WRITE, ...). Method-level checks require @EnableMethodSecurity on the config class.

5. JWT ⭐

A JSON Web Token is a compact, self-contained way to represent claims (identity + metadata) that the server can verify without a database lookup or server-side session store — this is what makes JWT-based auth stateless and horizontally scalable.

header.payload.signature
// eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6IkFETUlOIn0 . 5mhBHqs5_DTLdINd9...
PartContains
HeaderAlgorithm used to sign (e.g. HS256), token type
Payload (claims)subject (user id), roles, issued-at, expiration — Base64-encoded, NOT encrypted, readable by anyone
SignatureHMAC (or RSA) of header+payload using a server-side secret key — this is what proves the token wasn't tampered with

Critical point: the payload is only Base64-encoded, not encrypted — never put secrets (passwords, credit card numbers) in a JWT claim, anyone can decode it. What the signature guarantees is integrity (nobody altered the claims), not confidentiality.

// Issuing a token at login
String token = Jwts.builder()
    .setSubject(user.getEmail())
    .claim("role", user.getRole())
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + 900_000))  // 15 min
    .signWith(secretKey, SignatureAlgorithm.HS256)
    .compact();

// Validating on every request (in a custom filter)
Claims claims = Jwts.parserBuilder().setSigningKey(secretKey).build()
    .parseClaimsJws(token).getBody();
String email = claims.getSubject();

The server validates a token purely by re-checking the signature with its own secret key and the expiry — no database round-trip, no session store, which is why JWT auth scales horizontally with zero shared session state between instances.

6. Access & Refresh Tokens

Access tokenRefresh token
LifespanShort (minutes) — limits damage if leakedLong (days/weeks)
Sent onEvery API request (Authorization header)Only to a dedicated /auth/refresh endpoint
StorageMemory / short-livedOften stored server-side (DB) so it can be revoked

Why two tokens instead of one long-lived one: a short access token limits the blast radius of a leaked token (it expires soon), while the refresh token lets the client silently get a new access token without forcing the user to log in again. Rotation — issuing a new refresh token every time one is used, and invalidating the old one — detects theft: if a stolen refresh token is used after the legitimate client already rotated it, the reused old token is a signal of compromise.

7. OAuth2 Basics

OAuth2 is an authorization framework — it lets a user grant a third-party app limited access to their resources on another service (e.g. "Sign in with Google") without sharing their password with that app.

RoleExample
Resource OwnerThe user
ClientYour Spring Boot app
Authorization ServerGoogle/GitHub — issues tokens after login+consent
Resource ServerThe API that holds the protected data (can be the same as the auth server)

Authorization Code flow (most common for server-side web apps): user is redirected to the provider to log in and consent → provider redirects back with a short-lived code → your server exchanges that code (plus a client secret) for tokens server-to-server, so the access token never touches the browser directly. Spring Boot supports this via spring-boot-starter-oauth2-client.

8. CORS & CSRF

CORSCSRF
ProtectsThe server — controls which browser-origins are allowed to call it via JS (fetch/XHR)The user — prevents a malicious site from tricking the browser into making an unwanted authenticated request using the user's existing cookies
Enforced byThe browser, based on server response headersThe server, via a token the attacker's page can't obtain
Relevant whenFrontend and backend are on different originsAuth relies on cookies (ambient credentials automatically sent by the browser)
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://myfrontend.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

Why JWT-in-header APIs typically disable CSRF: CSRF exploits the browser automatically attaching cookies to requests. A JWT sent explicitly in an Authorization header (not a cookie) isn't automatically attached by the browser to a cross-site request, so the classic CSRF attack doesn't apply — this is why .csrf(csrf -> csrf.disable()) is common for stateless token APIs, but NOT if you ever store the JWT in a cookie.

9. End-to-End: Register → Login → Protected Route

POST /auth/register  { "email": "...", "password": "..." }
  → hash password (BCrypt) → save User → 201 Created

POST /auth/login  { "email": "...", "password": "..." }
  → AuthenticationManager verifies credentials against stored hash
  → issue access token (short) + refresh token (long) → 200 OK

GET /users/profile
  Header: Authorization: Bearer 
  → JwtAuthFilter validates signature + expiry, populates SecurityContext
  → @PreAuthorize / authorizeHttpRequests rule checks role → 200 OK, or 401/403
