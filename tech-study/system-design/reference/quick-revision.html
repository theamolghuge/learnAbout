DB scaling order of operations

Index properly → Read replicas (read-heavy) → Cache aggressively
  → Shard (only once a single primary can't handle write volume)

System design question — first 5 minutes

1. Clarify functional + non-functional requirements (scale, read/write ratio, latency)
2. Estimate scale — back-of-envelope requests/sec, storage growth
3. High-level design — major components + data flow
4. Deep dive on 1-2 components the interviewer cares about
5. Name the trade-offs explicitly — there's no single "correct" answer

30-second answers

CAP theorem, cleanly?
Partition tolerance isn't optional — the real choice during a partition is consistency vs availability.

Why is Kubernetes Secret not "secure" by default?
Base64 is encoding, not encryption — need etcd encryption-at-rest or an external secrets manager.

Read replica vs shard?
Replica scales reads only. Shard scales reads AND writes, at the cost of cross-shard query complexity.

Implement from memory

  • A Deployment + Service YAML pair for a Spring Boot app
  • Explain cache-aside vs write-through with a concrete example
  • Explain CAP with a concrete CP system and a concrete AP system
  • Whiteboard a "design a URL shortener" in 5 structured steps
