1. Kubernetes Core Objects ⭐

Kubernetes (k8s) orchestrates containers across a cluster of machines — deciding where they run, restarting them on failure, and routing traffic to them.

ObjectWhat it is
PodThe smallest deployable unit — one or more tightly-coupled containers that share network/storage. Usually one container per Pod for a Spring Boot app.
DeploymentDeclares the desired state for a set of identical Pods (how many replicas, which image) — k8s continuously reconciles reality to match, restarting crashed Pods automatically
ServiceA stable network endpoint in front of a changing set of Pods — Pods come and go (new IPs each time), but the Service's DNS name/IP stays constant, and it load-balances across whichever Pods currently match its label selector
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3                       # k8s keeps exactly 3 Pods running
  selector:
    matchLabels: { app: order-service }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      containers:
        - name: order-service
          image: myregistry/order-service:1.0
          ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector: { app: order-service }   # routes to any Pod with this label
  ports: [{ port: 80, targetPort: 8080 }]

Why a Pod's IP can't be relied on directly: if a Pod crashes, k8s replaces it with a brand new Pod that gets a brand new IP. A Service abstracts this away — other services/clients always talk to the stable Service name, and k8s handles routing to whichever Pods are currently healthy.

2. ConfigMap, Secret & Namespace

ObjectPurpose
ConfigMapNon-sensitive configuration (e.g. a feature flag, a log level) injected into Pods as env vars or mounted files — decouples config from the container image
SecretSame idea, for sensitive data (DB passwords, API keys) — base64-encoded at rest (not encryption by itself; real security needs an encryption-at-rest provider or an external secret manager)
NamespaceA virtual cluster within a cluster — isolates resources (e.g. separate dev/staging/prod namespaces) so names don't collide and access can be scoped per team/environment

3. Scaling in Kubernetes

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa }
spec:
  scaleTargetRef: { kind: Deployment, name: order-service }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

The Horizontal Pod Autoscaler automatically adjusts the replica count based on observed metrics (CPU, memory, or custom metrics) — this is Kubernetes-native horizontal scaling, the cluster equivalent of adding/removing EC2 instances behind a load balancer.

4. Scalability & Load Balancing ⭐

Vertical scalingHorizontal scaling
ApproachBigger machine — more CPU/RAM on one instanceMore machines — add instances, distribute load
CeilingHard hardware limit eventuallyEffectively unlimited (in theory)
DowntimeUsually requires a restart to resizeAdd/remove instances with no downtime
State requirementNone — one instance is fine with local stateRequires stateless instances (or externalized state) so any instance can serve any request

Horizontal scaling is the default target for modern web backends — it's why "Spring beans should be stateless" (from the Spring Core topic) matters at the architecture level too: any request-handling instance must be interchangeable, with shared state (sessions, cache) externalized to something like Redis, not held in instance memory.

Load balancer algorithms: round robin (rotate evenly), least connections (send to the instance with fewest active requests), and IP hash (same client always → same instance, useful for sticky sessions, though stateless design avoids needing this).

5. Caching

LayerExample
Client-side / CDNBrowser cache, CloudFront — caches static assets close to the user
Application-levelRedis/Memcached — cache expensive DB query results or computed data, shared across all app instances
Database-levelQuery cache, buffer pool — largely automatic, less in your control

Cache invalidation (famously "one of the two hard things in computer science") — common strategies:

StrategyHow it works
TTL (time-to-live)Entry auto-expires after N seconds — simple, but can serve slightly stale data
Write-throughUpdate the cache at the same time as the database — cache always current, adds write latency
Cache-aside (lazy loading)App checks cache first; on a miss, reads the DB and populates the cache — most common pattern, cache can go stale until next miss/TTL
Explicit invalidationDelete/update the cache entry directly when the underlying data changes — most accurate, most code to get right

6. Database Scaling & Indexing

TechniqueHow it helps
Read replicasCopies of the DB that serve read traffic, offloading the primary — writes still go to one primary. Good when reads vastly outnumber writes.
Sharding (horizontal partitioning)Split data across multiple DBs by some key (e.g. userId range) — each shard handles a subset of data, scaling both reads and writes. Adds real complexity: cross-shard queries/joins become hard.
IndexingSee SQL Notes §6 — the first, cheapest lever before reaching for replicas/sharding
Connection poolingSee SQL Notes §10 — reuse connections instead of the DB running out under load

Order of operations in an interview: index properly → add read replicas for read-heavy load → cache aggressively → only reach for sharding once a single primary genuinely can't handle write volume. Jumping straight to sharding is a common interview red flag — it's the most complex, expensive-to-reverse option.

7. CAP Theorem ⭐

In a distributed system, when a network partition occurs (nodes can't talk to each other), you must choose between:

PropertyMeans
Consistency (C)Every read gets the most recent write, or an error — never stale data
Availability (A)Every request gets a (non-error) response — even if it might be stale
Partition tolerance (P)The system keeps working despite network failures between nodes

The actual claim: partition tolerance is not optional for any real distributed system (networks fail — you don't get to choose P away). So CAP really forces a choice between C and A specifically during a partition: CP systems refuse to serve a request they can't guarantee is consistent (may return an error/timeout); AP systems serve a response anyway, possibly stale, favoring uptime. Outside of an actual partition, most systems provide both C and A just fine — this is the detail interviewers listen for; a naive "CAP means pick 2 of 3 always" answer is a common miss.

SystemTypically favors
Traditional RDBMS with synchronous replication (e.g. banking)CP — correctness over uptime
DNS, many NoSQL stores (Cassandra, DynamoDB default mode)AP — uptime over strict consistency, often offering "eventual consistency" instead

8. Rate Limiting

AlgorithmHow it works
Fixed windowCount requests in fixed time buckets (e.g. per minute) — simple, but allows a burst right at a window boundary (2x the limit across the boundary)
Sliding windowConsiders a rolling time window instead of fixed buckets — smooths out the boundary-burst problem, more accurate
Token bucketA bucket refills with tokens at a steady rate; each request consumes a token, request rejected if the bucket is empty — allows controlled bursts up to the bucket size while enforcing an average rate

Rate limiting protects backend services from being overwhelmed (accidental retry storms or deliberate abuse) — typically enforced at the API Gateway (previous topic) so individual services don't each need to implement it.

9. Approaching a System Design Question

1. Clarify requirements — functional (what must it do) and
   non-functional (scale: how many users/requests, read vs write ratio, latency needs)
2. Estimate scale — back-of-envelope: requests/sec, storage growth, peak vs average load
3. High-level design — draw the major components and how data flows between them
4. Deep dive — pick 1-2 components the interviewer cares about and go deep
   (e.g. "how does the database handle this write volume specifically")
5. Discuss trade-offs explicitly — every choice (SQL vs NoSQL, cache vs no cache,
   sync vs async) has a cost; naming it shows judgment, not just knowledge
6. Address bottlenecks & failure modes — what breaks first under load,
   what happens if a component goes down

At 5 years experience, interviewers are listening for trade-off reasoning, not a "correct" architecture — there usually isn't one. Naming the trade-off you're making and why (e.g. "I'd cache this at the cost of possible staleness, because read volume is 100x write volume here") demonstrates the judgment a senior-ish role actually requires.
