Kubernetes

Why does Kubernetes need a Service object in front of Pods instead of clients just talking to Pod IPs directly?

Pods are ephemeral — when one crashes or is rescheduled, its replacement gets a brand new IP address. A Service provides a stable DNS name/IP that doesn't change, and load-balances traffic across whichever Pods currently match its label selector, so clients never need to track individual Pod lifecycles.

What's the relationship between a Deployment and its Pods?

A Deployment declares the desired state — which image, how many replicas — and Kubernetes continuously reconciles actual cluster state to match it. If a Pod crashes or is deleted, the Deployment's controller notices the replica count has dropped below the desired number and creates a replacement automatically.

Are Secrets in Kubernetes actually encrypted?

Not by default — Secret values are only base64-encoded, which is trivially reversible, not real encryption. Genuine protection requires enabling encryption-at-rest for the cluster's etcd store or using an external secrets manager (e.g. AWS Secrets Manager, HashiCorp Vault) — a common interview trap is assuming "Secret" implies encryption on its own.

Scalability

Why is horizontal scaling generally preferred over vertical scaling for web backends?

Vertical scaling (a bigger machine) hits a hard hardware ceiling and typically requires downtime to resize. Horizontal scaling (more machines) has effectively no ceiling and can add/remove capacity without downtime — the cost is that your application must be stateless (or externalize state) so any instance can serve any request, which is why "stateless services" is a recurring theme from the Spring Core topic onward.

Caching

Explain the cache-aside pattern.

The application checks the cache first; on a miss, it reads from the database, then populates the cache with that result before returning it. It's the most common caching pattern because it's simple and only caches data that's actually requested, but entries can go stale until the next miss or a TTL expiry, so it's best paired with a TTL or explicit invalidation for data that changes.

What's the trade-off of write-through caching versus cache-aside?

Write-through updates the cache at the same moment as the database write, so the cache is never stale for that entry — at the cost of added latency on every write, since two systems must be updated. Cache-aside only touches the cache on reads (populating it lazily), keeping writes fast but allowing a window where the cache can be stale relative to the database.

Database Scaling

What's the difference between a read replica and sharding, and when would you reach for each?

A read replica is a full copy of the database that serves read-only traffic, offloading the primary — good when read volume is the bottleneck and write volume is manageable on one primary. Sharding splits the data itself across multiple databases by some key, scaling both reads and writes but introducing real complexity (cross-shard queries and joins become hard). The general order is: index properly, add read replicas, cache aggressively, and only shard once a single primary genuinely can't handle write volume.

CAP Theorem

What does the CAP theorem actually say, and what's a common misconception about it?

During a network partition, a distributed system must choose between Consistency (every read reflects the latest write, or errors) and Availability (every request gets a response, possibly stale). The common misconception is treating it as "pick any 2 of C, A, P at all times" — partition tolerance isn't optional for a real distributed system, since networks do fail. The actual choice is only forced between C and A, and only during an actual partition; most of the time, systems provide both.

Give an example of a system that favors CP and one that favors AP.

A traditional relational database used for banking transactions favors CP — it would rather return an error than risk showing a stale/incorrect balance. DNS and many NoSQL stores like Cassandra or DynamoDB in their default configuration favor AP — they'd rather keep serving requests (possibly with slightly stale data) than go down, using eventual consistency as the trade-off.

Rate Limiting

What's the problem with a naive fixed-window rate limiter, and how does token bucket address it?

A fixed window (e.g. "100 requests per minute, resetting on the minute") allows a burst of up to double the limit right around a window boundary — 100 requests in the last second of one window plus 100 in the first second of the next. Token bucket refills tokens at a steady rate and allows a request only if a token is available, smoothing enforcement into a consistent average rate while still permitting some controlled burstiness up to the bucket's capacity.

General approach

You're asked an open-ended system design question with no further detail. What's your first move?

Clarify requirements before designing anything — both functional (what must the system actually do) and non-functional (expected scale, read/write ratio, latency requirements). Jumping straight to a diagram without pinning down scale is a common mistake; the right design for 1,000 users and for 100 million users can look completely different.
