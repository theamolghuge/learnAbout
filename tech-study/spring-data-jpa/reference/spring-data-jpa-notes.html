1. JPA & Hibernate

JPA (Jakarta Persistence API) is a specification — a set of interfaces/annotations for mapping Java objects to relational tables (ORM). Hibernate is the most common implementation of that spec. Spring Data JPA sits on top of both, eliminating boilerplate by generating repository implementations from interfaces.

Your code → Spring Data JPA (repository interfaces)
          → JPA (spec: EntityManager, @Entity, JPQL)
          → Hibernate (implementation, generates SQL)
          → JDBC (§ previous topic)
          → Database

2. Entities & Mapping

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // DB auto-increment
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(name = "created_at")
    private Instant createdAt;

    protected User() {}   // JPA requires a no-arg constructor (can be protected)

    public User(String email) { this.email = email; }
    // getters/setters
}
StrategyHow IDs are generated
IDENTITYDB auto-increment column — simple, but can't batch inserts efficiently
SEQUENCEDB sequence object — allows batching, Hibernate's generally preferred choice on Postgres
AUTOLet the provider pick based on the DB dialect

3. Entity Relationships ⭐

AnnotationRepresentsExample
@OneToOne1:1User ↔ UserProfile
@OneToMany1:N (inverse side)Customer → many Orders
@ManyToOneN:1 (owning side — holds the FK)Order → one Customer
@ManyToManyN:N, needs a join tableStudent ↔ many Courses
@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List orders = new ArrayList<>();
}

@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)          // Order is the owning side — holds the FK column
    @JoinColumn(name = "customer_id")
    private Customer customer;
}

Owning side: the side with @JoinColumn is the one that actually holds the foreign key in the database and controls the relationship on save. The other side uses mappedBy to say "I'm just the inverse view of that FK, don't create a second join column." Always put @ManyToOne on the "many" side — it naturally corresponds to where the FK column lives.

@Entity
public class Student {
    @ManyToMany
    @JoinTable(name = "student_course",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set courses = new HashSet<>();
}

4. Repositories

public interface UserRepository extends JpaRepository {

    // Derived query — Spring parses the method name and generates the query
    Optional findByEmail(String email);
    List findByCreatedAtAfter(Instant date);
    boolean existsByEmail(String email);
    List findByRoleAndActiveTrue(String role);
}

JpaRepository<User, Long> gives you save(), findById(), findAll(), deleteById(), count() for free — no implementation code, Spring generates a proxy at startup. Derived query methods follow a naming convention (findBy + property + optional operator like After/Containing/OrderBy) that Spring Data parses into a query without you writing SQL or JPQL at all.

5. JPQL & Native Queries

JPQL queries entities and their fields (object-oriented), not tables and columns — it's translated to SQL by Hibernate, so it stays portable across databases.

public interface OrderRepository extends JpaRepository {

    @Query("SELECT o FROM Order o WHERE o.customer.id = :customerId AND o.total > :min")
    List findLargeOrders(@Param("customerId") Long customerId, @Param("min") BigDecimal min);

    // Native SQL — escape hatch for DB-specific features (window functions, etc.)
    @Query(value = "SELECT * FROM orders WHERE total > :min ORDER BY total DESC LIMIT 10", nativeQuery = true)
    List findTop10ByTotal(@Param("min") BigDecimal min);
}

Prefer derived query methods for simple lookups, JPQL for anything needing joins/aggregation that stays portable, and native queries only when you need a DB-specific feature JPQL can't express.

6. Pagination & Sorting

public interface OrderRepository extends JpaRepository {
    Page findByCustomerId(Long customerId, Pageable pageable);
}

Pageable pageable = PageRequest.of(0, 20, Sort.by("createdAt").descending());
Page page = orderRepository.findByCustomerId(customerId, pageable);

page.getContent();       // the 20 orders on this page
page.getTotalElements(); // total count across all pages (extra COUNT query)
page.getTotalPages();

Page<T> runs an extra COUNT query to know the total — for infinite-scroll style APIs where you don't need a total count, Slice<T> avoids that extra query and just tells you if there's a next page.

7. Lazy vs Eager Loading & the N+1 Problem ⭐

StrategyBehaviorDefault for
FetchType.LAZYRelated entity loaded only when accessed — a proxy is fetched initially@OneToMany, @ManyToMany
FetchType.EAGERRelated entity loaded immediately, in the same or an additional query@ManyToOne, @OneToOne

The N+1 problem: fetch 1 list of N parent entities (1 query), then lazily access a collection on each one inside a loop — that's N additional queries, one per parent, instead of one query joining everything.

List customers = customerRepository.findAll();   // 1 query
for (Customer c : customers) {
    c.getOrders().size();   // LAZY — triggers 1 query PER customer = N extra queries
}

Fixes:

// 1. JOIN FETCH in JPQL — pulls related entities in the same query
@Query("SELECT DISTINCT c FROM Customer c LEFT JOIN FETCH c.orders")
List findAllWithOrders();

// 2. @EntityGraph — declarative alternative to JOIN FETCH
@EntityGraph(attributePaths = "orders")
List findAll();

// 3. Batch fetching — groups the N queries into fewer IN(...) queries
@BatchSize(size = 20)
private List orders;

Interview rule of thumb: default relationships to LAZY everywhere (including @ManyToOne/@OneToOne, overriding the EAGER default), and fetch what you actually need explicitly per query — this avoids both N+1 and accidentally loading huge unrelated object graphs.

8. Transactions

@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        inventoryService.reserve(order.getItems());   // if this throws, the save above rolls back too
    }
}

@Transactional wraps the method in a database transaction — by default it rolls back on any unchecked exception, but NOT on checked exceptions (you can override with rollbackFor = Exception.class). It's implemented via a Spring AOP proxy, which is why calling an @Transactional method from within the same class (self-invocation) bypasses the proxy and the transaction silently doesn't apply.

PropagationBehavior
REQUIRED (default)Join the existing transaction, or start a new one if none exists
REQUIRES_NEWAlways start a new, independent transaction — suspends any existing one
NESTEDStart a savepoint within the existing transaction — can roll back to just that point

9. Validation

public class CreateUserRequest {

    @NotBlank(message = "name is required")
    private String name;

    @Email
    @NotBlank
    private String email;

    @Min(18) @Max(120)
    private int age;

    @Size(min = 8, message = "password must be at least 8 characters")
    private String password;
}

@PostMapping
public UserDto create(@RequestBody @Valid CreateUserRequest request) {
    return userService.create(request);   // never reached if validation fails
}
AnnotationChecks
@NotNullNot null (but empty string/collection still passes)
@NotBlankNot null and not just whitespace — for Strings
@NotEmptyNot null and size > 0 — for Strings/collections
@Size(min=, max=)Length/size bounds
@Min / @MaxNumeric bounds
@EmailValid email format
@Pattern(regexp=)Matches a regex

@Valid on a @RequestBody parameter tells Spring MVC to run Bean Validation before the handler body executes. A failure throws MethodArgumentNotValidException — which is exactly what the global exception handler below catches to return a proper 400.

10. Exception Handling ⭐

public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long id) {
        super("User not found: " + id);
    }
}

@RestControllerAdvice   // = @ControllerAdvice + @ResponseBody on every method
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity handleNotFound(UserNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse("NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)   // thrown by failed @Valid
    public ResponseEntity handleValidation(MethodArgumentNotValidException ex) {
        String message = ex.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining(", "));
        return ResponseEntity.badRequest().body(new ErrorResponse("VALIDATION_ERROR", message));
    }

    @ExceptionHandler(Exception.class)   // catch-all — never leak stack traces to clients
    public ResponseEntity handleUnexpected(Exception ex) {
        log.error("Unhandled exception", ex);
        return ResponseEntity.internalServerError().body(new ErrorResponse("INTERNAL_ERROR", "Something went wrong"));
    }
}

record ErrorResponse(String code, String message) {}

Why centralize this: without @ControllerAdvice, every controller method would need its own try/catch to produce consistent error JSON — duplicated everywhere and easy to get inconsistent. One class intercepts exceptions thrown from any controller and maps each exception type to the right HTTP status and response shape. Handlers are matched most-specific-exception-type first, so a specific UserNotFoundException handler wins over the generic Exception catch-all.
