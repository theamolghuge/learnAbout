JPA / Hibernate

What's the relationship between JPA, Hibernate, and Spring Data JPA?

JPA is a specification for ORM in Java — interfaces and annotations, no implementation. Hibernate is the most widely used implementation of that spec, doing the actual SQL generation and object mapping. Spring Data JPA sits on top of both, eliminating boilerplate by generating repository implementations from interface method signatures.

Relationships

What does "owning side" mean in a bidirectional @OneToMany/@ManyToOne relationship?

The owning side is the entity that holds the foreign key column and is annotated with @JoinColumn — it's the side JPA actually looks at to persist/update the relationship. The other side uses mappedBy to declare itself as the inverse, read-only view. In a Customer↔Order relationship, Order is the owning side (it has customer_id), so setting the relationship only on the Customer side without updating Order won't persist correctly.

Why does @ManyToOne default to EAGER while @OneToMany defaults to LAZY?

JPA assumes a "many" side entity typically needs its single related "one" (e.g. an Order usually needs its Customer), while a collection (@OneToMany) could be arbitrarily large and expensive to load unconditionally. In practice, most teams override both to LAZY by default and fetch explicitly per-query to avoid both N+1 problems and unexpectedly large loads.

Repositories

How does a method like findByEmailAndActiveTrue(String email) work without you writing a query?

Spring Data JPA parses the method name at startup using its keyword convention — "findBy" + property names joined by "And"/"Or", with optional suffixes like "True", "After", "Containing" — and generates the equivalent JPQL query automatically, creating a proxy implementation of the repository interface.

When would you write a @Query instead of relying on a derived method name?

When the logic is too complex to express cleanly as a method name (multiple joins, conditional filters, aggregations), or when you need a native SQL feature JPQL doesn't support (window functions, DB-specific syntax). Derived methods are best for simple, single-purpose lookups.

Lazy/Eager & N+1

Explain the N+1 query problem with an example.

You fetch a list of N parent entities with one query, then access a LAZY collection on each one inside a loop — each access triggers its own separate query to fetch that entity's related rows, resulting in 1 (parents) + N (one per parent's lazy collection) queries instead of a single joined query. It's a very common accidental performance bug in ORMs.

How do you fix an N+1 problem in Spring Data JPA?

Use JOIN FETCH in a JPQL query to pull the related entities in the same query, or the equivalent @EntityGraph annotation for a more declarative approach. For less predictable access patterns, @BatchSize groups the N individual queries into fewer batched IN(...) queries instead of eliminating them entirely.

Transactions

Does @Transactional roll back on every exception?

No — by default it only rolls back on unchecked exceptions (RuntimeException and its subclasses). A checked exception thrown inside the method does NOT trigger a rollback unless you explicitly configure rollbackFor = Exception.class. This is a common source of bugs when checked exceptions are used for business errors inside transactional methods.

Why does calling an @Transactional method from another method in the same class not apply the transaction?

Spring implements @Transactional via an AOP proxy wrapped around the bean. External callers go through the proxy, which starts the transaction before delegating to the real method. A call from within the same class goes directly to "this" — bypassing the proxy entirely — so the transactional behavior silently doesn't apply. The fix is to move the transactional method to a separate bean/class, or inject a self-reference.

Validation

What happens when @Valid fails on a @RequestBody parameter?

Spring throws a MethodArgumentNotValidException before the controller method body ever executes — the handler code never runs. That exception carries a BindingResult with every field error, which a global @ExceptionHandler typically catches to build a structured 400 response listing all the validation failures.

Difference between @NotNull, @NotEmpty, and @NotBlank?

@NotNull only rejects null — an empty string or empty list still passes. @NotEmpty additionally rejects empty (size 0) — works on Strings and collections. @NotBlank is String-specific and additionally rejects whitespace-only strings. For a required text field, @NotBlank is almost always the right one.

Exception Handling

What does @ControllerAdvice/@RestControllerAdvice do?

It defines a global, cross-cutting handler for exceptions thrown by any @Controller/@RestController in the app — instead of every controller needing its own try/catch, one class centralizes the mapping from exception type to HTTP status and response body. @RestControllerAdvice additionally applies @ResponseBody to every handler method, so responses are serialized as JSON directly.

If you have handlers for both UserNotFoundException and the generic Exception, which one runs when a UserNotFoundException is thrown?

The most specific matching handler — @ExceptionHandler resolution prefers the closest type match in the exception's class hierarchy, so the UserNotFoundException-specific handler runs, not the generic Exception catch-all.

Why should the catch-all Exception handler never return the raw exception message or stack trace to the client?

It can leak internal implementation details (class names, SQL, file paths) useful to an attacker, and it's a poor experience for legitimate clients who get an unstructured, unstable message. Log the full exception server-side, and return a generic, stable error code/message to the client.
