1. Git Basics

git clone               # copy a remote repo locally
git status                    # what's changed, staged vs unstaged
git add file.java             # stage a change
git commit -m "message"       # snapshot staged changes
git push origin main          # send local commits to the remote
git pull                       # fetch + merge remote changes into current branch
git log --oneline --graph     # visualize commit history

Git tracks content as a series of commits — immutable snapshots, each pointing to its parent(s), forming a directed acyclic graph. A branch is just a movable pointer to a commit; HEAD is a pointer to whichever branch (or commit) you currently have checked out.

2. Branching & Merging ⭐

git checkout -b feature/add-login    # create + switch to a new branch
git switch main                       # newer syntax for switching branches
git merge feature/add-login           # merge feature branch into current branch
Merge typeWhen it happensHistory shape
Fast-forwardTarget branch has no new commits since the feature branched offLinear — target pointer just moves forward, no merge commit
3-way mergeBoth branches have diverged (new commits on each)A new merge commit with two parents, preserving both histories

3. Rebase vs Merge

git checkout feature/add-login
git rebase main             # replays feature's commits on top of main's latest tip
mergerebase
HistoryPreserves exact history, adds a merge commitRewrites commits — replays them onto a new base, linear history
Commit hashesUnchangedChanged — every replayed commit gets a new hash
Safe on shared branches?Yes, alwaysNever rebase commits already pushed/shared — rewrites history other people have, breaking their local copies
Common useMerging a finished feature branch into mainCleaning up your own local feature branch before opening a PR (squash noisy WIP commits, catch up with main)

Golden rule: never rebase (or force-push) a branch other people have already pulled from — it rewrites commit history, and their local branch will diverge irreconcilably from the rewritten one.

4. PR Workflow & Resolving Conflicts

git checkout -b feature/x
# ...make commits...
git push -u origin feature/x
# open a Pull Request on GitHub/GitLab → code review → merge

A merge conflict happens when two branches changed the same lines (or one edited a file the other deleted) and Git can't automatically reconcile them.

git merge main
# CONFLICT (content): Merge conflict in OrderService.java

<<<<<<< HEAD
double total = price * 1.08;
=======
double total = price * quantity * 1.08;
>>>>>>> main

# Manually edit the file to keep the correct code, then:
git add OrderService.java
git commit          # completes the merge

Code review on a PR typically checks correctness, test coverage, and design — not just "does it work." Small, focused PRs get reviewed faster and more thoroughly than large ones.

Build lifecycle — each phase runs everything before it

mvn validate → compile → test → package → verify → install → deploy

mvn clean       # deletes the target/ build output directory
mvn test        # compiles + runs tests
mvn package     # produces the jar/war in target/
mvn clean install   # full clean build, installs the jar to your local ~/.m2 repo

The parent POM pattern (spring-boot-starter-parent) centrally manages compatible dependency versions — this is why you usually don't specify a version on individual Spring Boot starter dependencies; the parent's dependency management picks a tested, compatible version for you.

6. Gradle (brief)

// build.gradle
plugins { id 'org.springframework.boot' version '3.3.0' }

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
MavenGradle
Config formatXML (pom.xml)Groovy or Kotlin DSL (build.gradle) — more concise
Build speedSlower — less caching by defaultFaster — incremental builds, build cache, daemon process
FlexibilityConvention over configuration, more rigid lifecycleMore programmable/scriptable — also a double-edged sword (harder to reason about)
PrevalenceStill the majority in enterprise Java/Spring shopsCommon in Android and newer projects

Interview-level knowledge here is usually: know the syntax looks different, know Gradle is generally faster due to incremental builds/caching, and be able to read a build.gradle even if you mainly use Maven day to day.

7. Postman

A GUI client for manually constructing and sending HTTP requests — used to exercise an API during development before (or instead of) writing automated tests, inspect raw responses/headers/status codes, and share request collections with a team. Supports environment variables (swap base URLs between dev/staging/prod), pre-request scripts (e.g. fetch an auth token), and collection-level test assertions written in JavaScript.

8. Swagger / OpenAPI

OpenAPI is a specification format (JSON/YAML) for describing a REST API's endpoints, request/response shapes, and auth requirements. Swagger UI is the most common tool that renders an OpenAPI spec as interactive, browsable documentation.

// pom.xml — springdoc generates the spec automatically from your controllers

    org.springdoc
    springdoc-openapi-starter-webmvc-ui
    2.5.0


// annotate for richer docs (optional — a baseline spec is generated with none of this)
@Operation(summary = "Get a user by id")
@ApiResponse(responseCode = "404", description = "User not found")
@GetMapping("/{id}")
public UserDto getUser(@PathVariable Long id) { ... }

With springdoc-openapi on the classpath, Spring Boot auto-generates the spec from your @RestController classes and serves interactive docs at /swagger-ui.html — consumers of your API (frontend team, other services) can browse and even try requests directly from the browser, without needing separately-maintained documentation that drifts out of sync with the code.
