Git · Maven · API Tools

Git

What's the fundamental difference between merge and rebase?

Merge combines two branches' histories with a new merge commit that has two parents — nothing is rewritten, the original commits stay exactly as they were. Rebase replays your branch's commits one by one onto a new base, giving each replayed commit a brand new hash — the result is a cleaner, linear history, but it rewrites commit identity.

Why is it dangerous to rebase a branch that's already been pushed and pulled by teammates?

Rebase gives every replayed commit a new hash — from Git's perspective they're entirely different commits, even though the content is similar. Anyone who already has the old commits will find their local branch has diverged irreconcilably from the rewritten remote branch, typically requiring a forced reset on their end and potentially losing local work.

Walk through resolving a merge conflict.

Git marks the conflicting sections in the file with <<<<<<< HEAD, =======, and >>>>>>> markers showing both versions. You manually edit the file to the correct final content, removing the conflict markers, then git add the resolved file and git commit (or git rebase --continue if mid-rebase) to complete the operation.

What's a fast-forward merge, and when does Git use one automatically?

When the target branch has no new commits since the feature branch diverged from it, Git can simply move the target branch's pointer forward to the feature branch's tip — no merge commit needed, since there's nothing to reconcile. It only happens when history is still linear between the two branches.

Maven

What's the difference between compile, provided, runtime, and test dependency scopes?

compile (default) is available everywhere and packaged in the final artifact. provided is available at compile/test time but NOT packaged — you're assuming the deployment environment supplies it. runtime is needed to run but not to compile against (e.g. a JDBC driver, referenced only via reflection/SPI). test is only available while running tests, never packaged.

What does the Maven build lifecycle look like, and what does `mvn package` actually run?

The default lifecycle is an ordered sequence: validate → compile → test → package → verify → install → deploy, and running any phase runs every phase before it too. `mvn package` therefore compiles the code and runs the tests first, then produces the jar/war — it does not by itself install to the local repo or deploy.

What's the purpose of a parent POM like spring-boot-starter-parent?

It centrally manages dependency versions and plugin configuration for everything downstream — this is why individual Spring Boot starter dependencies in your pom.xml usually don't need an explicit version number; the parent has already pinned a tested, mutually-compatible set of versions, avoiding version-conflict bugs.

API Tools

What problem does OpenAPI/Swagger solve versus manually written API documentation?

Manually written docs drift out of sync with the actual code over time as endpoints change. With springdoc-openapi on the classpath, the spec is generated automatically from the real @RestController classes and their annotations, so the documentation can never fall behind the actual behavior of the API — and Swagger UI gives consumers an interactive page to try requests directly.

When would you reach for Postman versus an automated integration test?

Postman is for manual, exploratory testing during development — quickly hitting an endpoint, inspecting the raw response, iterating on request shape, or sharing a runnable request with a teammate/frontend dev. Automated tests (MockMvc, @SpringBootTest) are for regression protection that runs on every build without a human clicking anything — the two are complementary, not substitutes for each other.
