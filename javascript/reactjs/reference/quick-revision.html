React Query vs Redux vs Context

React Query (TanStack Query) Redux (RTK) Context
Primary purpose Server/async state — fetch, cache, sync Global client state — predictable updates, middleware Pass data through tree without prop drilling
Best for API data, pagination, mutations, background refetch Complex UI state, cross-feature workflows, devtools time-travel Theme, locale, auth snapshot, rarely changing config
Caching Built-in stale-while-revalidate, dedupe, garbage collection Manual (RTK Query adds server cache layer) None — value held in Provider state
Re-render behavior Only components using specific query/mutation Selector-based subscriptions with memoization All consumers re-render when value reference changes
Async handling First-class: loading, error, retry, optimistic updates Thunks / RTK Query / sagas (extra setup) Manual — fetch in Provider effect (anti-pattern at scale)
Boilerplate Low — useQuery, useMutation, keys Medium — slices, actions, store (RTK reduces pain) Low — Provider + hook
DevTools Query inspector — cache, refetch, timing Redux DevTools — action history React DevTools only
Anti-pattern Storing purely local UI toggles in Query cache Duplicating server cache already in React Query High-frequency updates (performance death)
Rule of thumb Default for anything from an API When client state is complex and shared widely When few consumers and low update frequency

SSR vs CSR vs SSG vs RSC

CSR SSR SSG RSC
HTML produced Minimal shell; JS builds UI in browser Full HTML per request on server Full HTML at build time Server renders components; stream to client
When HTML is built Runtime (client) Runtime (server, per request) Build time Runtime (server, per request or cached)
JS to browser Full app bundle Hydration bundle + app code Hydration bundle (static pages may be minimal) Only Client Components' JS shipped
SEO Poor without pre-render/SSR Excellent Excellent Excellent (server HTML includes RSC output)
First paint Slower (wait for JS) Faster (HTML immediate) Fastest (CDN-served static) Fast — less JS to parse
Data freshness Client fetches after load Fresh per request Stale until rebuild (ISR mitigates) Fresh — direct DB/API on server
Server cost Low (static hosting) High (compute per request) Low after build Medium — server component execution
Interactivity Full client After hydration After hydration Client islands hydrate selectively
Typical tools Vite SPA, CRA Next.js getServerSideProps, Remix loaders Next.js SSG, Astro static Next.js App Router (default Server Components)
Watch out for Blank shell, SEO, slow FCP TTFB, hydration mismatch, server load Rebuild latency for dynamic data Serializable props only; client boundary discipline

useMemo vs useCallback vs React.memo

useMemo useCallback React.memo
What it does Caches a computed value between renders Caches a function reference between renders Skips re-render of component if props shallow-equal
Returns Any memoized value (object, array, number, JSX) Stable function reference HOC wrapping a component
Deps array Yes — recompute when deps change Yes — new function when deps change Optional custom compare function
Primary use case Expensive calculation; stable object/array for child deps Stable handler passed to memoized child or effect dep Prevent re-render when parent re-renders but props same
Helps when Compute is costly OR referential equality matters downstream Child is wrapped in memo or listed in effect deps Component is pure and renders often with identical props
Does NOT help when Cheap compute; deps change every render anyway Child not memoized and doesn't care about reference Props are new objects/functions every parent render
Common pairing Pass memoized value to memo child Pass memoized callback to memo child Wrap child; parent uses useCallback/useMemo for props
Cost Memory + dep comparison each render Memory + dep comparison each render Shallow prop compare each parent render
Interview one-liner "Memoize the result" "Memoize the function identity" "Memoize the component render"
