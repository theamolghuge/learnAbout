Node.js Interview Q&A

Common senior-level questions with concise answers. Practice explaining aloud.

Event Loop

Q: Explain the Node.js event loop phases.

The event loop has six phases executed in order: timers (setTimeout/setInterval), pending callbacks (deferred I/O), idle/prepare (internal), poll (fetch new I/O events, may block), check (setImmediate), and close callbacks (socket.on('close')). Between each phase, Node drains the microtask queue (Promise callbacks) and then the nextTick queue. The loop continues until no more work is scheduled.

Q: What is the difference between process.nextTick and setImmediate?

process.nextTick runs before the event loop continues to the next phase — it's the highest priority async callback. setImmediate runs in the check phase, after the poll phase completes. In practice: nextTick can starve I/O if used recursively; setImmediate is safer for deferring work. Inside an I/O callback, setImmediate runs before setTimeout(0).

Q: What happens when you block the event loop?

All I/O callbacks, timers, and incoming HTTP requests stall. Latency spikes, health checks fail, and the process may appear hung. Detect with event-loop-lag monitoring or clinic.js. Fix by offloading CPU work to worker threads, using streams for large data, or moving heavy computation to a separate service.

Q: What is the output order of this code?

console.log('A');
setTimeout(() => console.log('B'), 0);
setImmediate(() => console.log('C'));
Promise.resolve().then(() => console.log('D'));
process.nextTick(() => console.log('E'));

A, E, D, then either B or C (timers vs check phase order varies by context), then the other. At top level outside I/O, setTimeout(0) may run before or after setImmediate depending on Node version and system timing.

Q: How does libuv's thread pool relate to the event loop?

Some operations (file system, DNS lookup, certain crypto/compression) run on libuv's thread pool (default 4 threads, configurable via UV_THREADPOOL_SIZE). When the thread completes, the callback enters the event loop's poll phase. The JS thread itself never blocks on these — but if all pool threads are busy, new file operations queue up.

Streams

Q: What are the four types of streams?

Readable (source — fs.createReadStream), Writable (sink — fs.createWriteStream), Duplex (both — TCP socket), and Transform (modifies data — zlib.createGzip). All are EventEmitters. Object mode streams carry JS objects instead of Buffers.

Q: What is backpressure and how do you handle it?

Backpressure occurs when a writable stream can't accept data as fast as the readable produces it. When writable.write() returns false, pause the readable. Resume on the writable's drain event. Use stream.pipeline() or stream/promises.pipeline() to handle this automatically with proper error propagation.

Q: Why use streams instead of reading a file into a Buffer?

Memory efficiency — a 1 GB file processed in 64 KB chunks uses constant memory. Streams also enable piping (file → gzip → HTTP response) without intermediate storage. For large uploads/downloads, streaming is mandatory to avoid OOM crashes.

Q: How do you consume a readable stream in modern Node?

Three ways: event-based (on('data')/on('end')), callback (readable.pipe(writable)), or async iteration: for await (const chunk of readable) { ... }. The async iterator approach is cleanest for transform logic in async functions.

Express

Q: How does Express middleware work?

Middleware functions have signature (req, res, next). Express executes them in registration order. Each can modify req/res, end the response, or call next() to pass control. Error middleware has 4 parameters (err, req, res, next) and must be registered last. If next(err) is called, Express skips to the next error handler.

Q: How do you structure a production Express app?

Separate concerns: routes, controllers, services, middleware. Order: helmet/cors → body parser → request logger → auth → routes → 404 handler → error handler. Use environment-based config. Don't put business logic in route handlers — delegate to service layer. Mount routers with app.use('/api/v1/users', userRouter).

Q: Express vs Fastify — when would you choose each?

Fastify is ~2-3x faster, has built-in schema validation (JSON Schema), and async-first middleware. Choose Fastify for performance-critical APIs and when you want schema-driven development. Choose Express for largest ecosystem, team familiarity, and legacy codebases. Both are production-ready.

Q: How do you handle async errors in Express route handlers?

Wrap in try/catch and call next(err), or use an async wrapper: const asyncHandler = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next). Without this, rejected promises in async handlers become unhandled rejections — they won't reach error middleware automatically (though Express 5 fixes this).

Auth

Q: JWT vs session cookies — trade-offs?

Sessions: server-side state (Redis), easy revocation, smaller cookies, requires session store. JWT: stateless, scales horizontally without shared store, but hard to revoke (need blocklist or short expiry + refresh tokens). JWT payload is readable (base64) — never store secrets in it. Use httpOnly secure cookies for refresh tokens; access tokens in memory or Authorization header.

Q: How should you store passwords?

Never plain text or reversible encryption. Use bcrypt (cost 10-12) or argon2. Each password gets a unique salt (bcrypt handles this). On login, compare with bcrypt.compare(). Never implement your own hashing. Add rate limiting on login endpoints to prevent brute force.

Q: What is refresh token rotation?

When a client uses a refresh token to get a new access token, also issue a new refresh token and invalidate the old one. If an old refresh token is reused (possible theft), revoke the entire token family. Store refresh tokens hashed in the database. Detect reuse as a security signal.

Q: How do you implement RBAC in Express?

After authentication middleware attaches user to req, authorization middleware checks roles: if (!req.user.roles.includes('admin')) return res.status(403).json(...). For resource-level permissions, check ownership: if (order.userId !== req.user.id && !req.user.roles.includes('admin')). Consider CASL or accesscontrol libraries for complex rules.

SQL

Q: What is the N+1 query problem?

Fetching a list of N items, then running 1 query per item for related data (N additional queries). Fix with JOINs, eager loading (include in Prisma), or DataLoader batching. Example: get 100 orders, then 100 separate queries for each order's user. Instead: one query with JOIN or include: { user: true }.

Q: Explain transaction isolation levels.

Read Uncommitted — dirty reads possible. Read Committed — only see committed data (PostgreSQL default). Repeatable Read — same query returns same rows within transaction. Serializable — full isolation, may cause serialization failures. Higher isolation = more consistency but more locking/retries. Use Read Committed for most apps; Serializable for financial operations.

Q: When should you use a database transaction?

When multiple writes must succeed or fail together: transfer money (debit + credit), create order + decrement inventory, insert record + outbox event. Don't wrap read-only operations. Keep transactions short to avoid lock contention. In Prisma: prisma.$transaction([...]) or interactive transactions with callback.

Q: How do indexes work and when can they hurt?

B-tree indexes speed up WHERE, JOIN, ORDER BY on indexed columns. Composite index column order matters — leftmost prefix rule. Too many indexes slow writes (each INSERT/UPDATE must update indexes). Don't index low-cardinality columns alone (boolean). Use EXPLAIN ANALYZE to verify query plans. Partial indexes for filtered queries.

Redis

Q: Explain the cache-aside pattern.

Application checks cache first. On miss, read from database, write result to cache with TTL, return data. On cache hit, skip DB entirely. On write/update, invalidate (delete) the cache key or update it. Simple and effective. Watch for race conditions: two concurrent misses can both hit DB — use locking or accept occasional duplicate reads.

Q: What happens when Redis goes down?

With cache-aside: requests fall through to the database — slower but functional (cache is not source of truth). Implement circuit breaker to avoid hammering a failing Redis. For session store or rate limiter in Redis: users get logged out or rate limits fail open/closed depending on policy. Use Redis Sentinel or Cluster for HA in production.

Q: Redis vs in-memory cache (Node Map)?

Redis: shared across multiple Node processes/instances, persistence options, rich data structures, TTL built-in, pub/sub. In-memory Map: faster (no network), but per-process only, lost on restart, no sharing between cluster workers. Use Redis when running multiple instances; in-memory for single-process caching of computed values with short TTL.

Q: How do you use Redis for rate limiting?

Sliding window with sorted sets: add timestamp as score, remove entries older than window, count remaining. Or use INCR with EXPIRE for fixed window (simpler but boundary burst issue). Libraries like rate-limiter-flexible abstract this. Store in Redis so limits apply across all app instances. Return 429 with Retry-After header.

Distributed Systems

Q: What is the Saga pattern?

A distributed transaction split into local transactions, each with a compensating action if a later step fails. Example: CreateOrder → ProcessPayment → ReserveInventory → Ship. If shipping fails, compensate: ReleaseInventory → RefundPayment → CancelOrder. Two styles: choreography (event-driven, decentralized) and orchestration (central coordinator). Prefer orchestration for complex flows with many steps.

Q: Explain the Transactional Outbox pattern.

Problem: you need to update DB and publish a message atomically — but they're different systems. Solution: write the event to an outbox table in the same DB transaction as the business write. A separate relay/poller reads unsent outbox rows and publishes to Kafka/RabbitMQ, then marks them sent. Guarantees at-least-once delivery without dual-write inconsistency.

Q: What is CQRS and when would you use it?

Command Query Responsibility Segregation separates write model (commands, business rules) from read model (optimized queries, denormalized views). They sync via events. Use when read and write patterns differ greatly — e.g., complex writes but heavy analytical reads. Trade-off: eventual consistency between write and read sides. Don't use for simple CRUD apps.

Q: How do idempotency keys prevent duplicate processing?

Client sends a unique key (UUID) with the request (header: Idempotency-Key). Server checks if key exists in store (Redis/DB). If found, return the cached response without reprocessing. If not, process the request, store result with the key, return response. Critical for payment APIs and webhook handlers where retries are common.

Q: What is a circuit breaker and why use it?

Prevents cascading failures when a downstream service is unhealthy. States: Closed (normal), Open (fail fast, don't call service), Half-Open (send test request). After N failures → open. After timeout → half-open. If test succeeds → closed. Libraries: opossum for Node. Combined with retries (with exponential backoff and jitter) and timeouts on every outbound call.

Q: At-least-once vs exactly-once delivery?

At-least-once: message delivered one or more times (consumer must be idempotent). Most common and practical. At-most-once: may lose messages but never duplicates. Exactly-once: hardest — requires transactional messaging or idempotent consumers + dedup. In practice, aim for at-least-once + idempotent handlers.

MongoDB

Q: When would you choose MongoDB over PostgreSQL?

When data is document-shaped (nested objects, arrays), schema changes frequently, you need horizontal sharding early, or write-heavy workloads with simple queries. Examples: content management, product catalogs, IoT telemetry, user activity feeds. Choose PostgreSQL when you need complex joins, strict ACID across entities, or ad-hoc analytical queries.

Q: How do MongoDB transactions compare to SQL?

Multi-document ACID transactions available since MongoDB 4.0 (replica set required). Single-document writes were always atomic. Transactions have overhead — design documents to minimize cross-document transactions when possible. SQL databases have decades of mature transaction support with more isolation level options.

Q: What is the aggregation pipeline?

MongoDB's data processing framework — stages like $match (filter), $group (aggregate), $lookup (join), $project (reshape), $sort, $limit. Similar to SQL GROUP BY + JOIN but pipeline-based. Example: $match status → $group by category → $sum revenue. Runs on the server, reducing data transfer to the app.

Q: How do you model relationships in MongoDB?

Three approaches: Embedding (one-to-few, data accessed together — address inside user doc). Referencing (one-to-many, many-to-many — store ObjectId, use $lookup or app-level join). Hybrid (embed frequently accessed fields, reference the rest). Denormalize for read performance; accept duplication trade-off.

gRPC

Q: When would you choose gRPC over REST?

Internal microservice communication where performance matters, strong typing is needed, and clients are other services (not browsers). gRPC uses HTTP/2 + Protocol Buffers for smaller/faster payloads and supports bidirectional streaming. Choose REST for public APIs, browser clients, and when human-readable JSON and broad tooling (curl, Postman) are priorities.

Q: What are the four gRPC call types?

Unary — single request, single response (like REST). Server streaming — client sends one request, server streams responses. Client streaming — client streams requests, server sends one response. Bidirectional streaming — both sides stream independently. Streaming is a major advantage over REST for real-time data feeds.

Q: How does gRPC handle schema evolution?

Protocol Buffer definitions (.proto files) define services and messages. Fields have numbered tags — never reuse tag numbers. Add new optional fields without breaking old clients (unknown fields ignored). Use reserved keyword for removed fields. Code generation produces typed client/server stubs in multiple languages. Breaking changes require careful versioning.

Q: Can browsers call gRPC directly?

Not natively — browsers can't send HTTP/2 trailers needed for gRPC. Use gRPC-Web with a proxy (Envoy, grpc-web proxy) that translates between gRPC-Web and gRPC. Alternatively, expose REST/GraphQL gateway for browser clients and gRPC for service-to-service. This is a common reason REST remains the public API choice.

Kubernetes

Q: Explain Pods, Deployments, and Services.

Pod: smallest deployable unit — one or more containers sharing IP/network. Usually one container per pod for Node apps. Deployment: manages pod replicas, rolling updates, rollbacks — you declare desired state (3 replicas). Service: stable network endpoint (ClusterIP for internal, LoadBalancer for external) that load-balances across pod replicas via label selectors.

Q: How do liveness and readiness probes work?

Liveness probe: is the container alive? If it fails, K8s restarts the pod. Hit your /health endpoint. Readiness probe: is the container ready to receive traffic? If it fails, pod is removed from Service endpoints but not restarted. Use readiness during startup (DB connection not yet established) and liveness for deadlock detection. Set appropriate initialDelaySeconds.

Q: How do you manage config and secrets in K8s?

ConfigMap: non-sensitive config (feature flags, API URLs) — mounted as env vars or files. Secret: sensitive data (DB passwords, API keys) — base64 encoded (not encrypted by default; use external secret managers like AWS Secrets Manager with CSI driver). Never bake secrets into Docker images. Inject at runtime via env vars from K8s secrets.

Q: What is a rolling update and how do you roll back?

Deployment gradually replaces old pods with new ones (default: maxUnavailable 25%, maxSurge 25%). Zero-downtime if readiness probes pass. Rollback: kubectl rollout undo deployment/node-api reverts to previous ReplicaSet. Keep old ReplicaSets for history. Use CI/CD to automate deploy → smoke test → auto-rollback on failure.

Q: Docker Compose vs Kubernetes — when to use each?

Docker Compose: local development, simple staging, single-host deployments. Fast to set up, easy to understand. Kubernetes: production at scale — multi-node, auto-scaling, self-healing, rolling updates, service discovery, network policies. The complexity cost is justified when you need HA, horizontal scaling, and multi-service orchestration across machines.
