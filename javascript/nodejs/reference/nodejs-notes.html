Senior Developer Core

A senior Node.js developer should be able to:

  • Explain why blocking the event loop is catastrophic and how to detect/fix it
  • Design RESTful APIs with proper error contracts, versioning, and documentation
  • Choose between SQL and MongoDB (or both) with clear trade-off reasoning
  • Implement auth securely (hashing, token rotation, RBAC) without rolling custom crypto
  • Handle failures gracefully: retries with backoff, circuit breakers, dead-letter queues
  • Write idempotent handlers for distributed systems (payment webhooks, queue consumers)
  • Profile and optimize: connection pools, caching layers, stream-based processing
  • Ship with CI/CD, containerization, health checks, and structured observability
  • Discuss Saga, Outbox, and CQRS patterns when asked about microservices consistency

Architecture / V8 / libuv

Node.js is a JavaScript runtime built on Chrome's V8 engine and libuv, a C library providing the event loop, thread pool, and async I/O.

Key components

  • V8 — compiles JS to machine code, manages heap/GC. Single-threaded for JS execution.
  • libuv — event loop (epoll/kqueue/IOCP), thread pool (default 4 threads) for file I/O, DNS, crypto, compression.
  • Node bindings — C++ layer connecting V8 to libuv and OS APIs.

Thread model

  • One main thread runs JS + event loop.
  • libuv thread pool handles blocking OS calls (fs, some crypto, zlib).
  • worker_threads spawn separate V8 isolates for CPU-bound work.
  • cluster forks processes to use multiple CPU cores for I/O-bound servers.
// CPU-bound work blocks the event loop — offload it
const { Worker } = require('worker_threads');
new Worker('./hash-worker.js', { workerData: bigPayload });

Modules

CommonJS (CJS)

const fs = require('fs');
module.exports = { readConfig };
// require() is synchronous; modules are cached after first load

ES Modules (ESM)

import fs from 'node:fs/promises';
export default function handler() {}
// "type": "module" in package.json enables ESM by default

Important behaviors

  • Module cache: require.cache — same module instance on repeated imports.
  • Circular deps: partially evaluated exports (often undefined) until both finish loading.
  • Dynamic import: await import('./module.js') — async, works in CJS too.
  • Path resolution: node_modules lookup, package.json exports field (conditional exports).

Async / Promises

Callback → Promise → async/await evolution

// Promisify legacy callbacks
const { promisify } = require('util');
const readFile = promisify(fs.readFile);

// Parallel vs sequential
const [a, b] = await Promise.all([fetchA(), fetchB()]);
const results = await Promise.allSettled(tasks); // never rejects

Error handling rules

  • async functions always return a Promise; thrown errors become rejections.
  • try/catch around await — mandatory for per-call error handling.
  • process.on('unhandledRejection') — log and exit in production (Node 15+ warns, later crashes).
  • Never mix callbacks and Promises in the same function without careful bridging.

Utility patterns

  • Promise.race — timeout wrappers
  • AbortController — cancel fetch/streams
  • Retry with exponential backoff + jitter for transient failures

Event Loop

The event loop is libuv's mechanism for scheduling callbacks. Understanding phases is the #1 Node.js interview topic.

Phases (in order)

  1. timers — setTimeout, setInterval callbacks
  2. pending callbacks — I/O callbacks deferred from previous iteration
  3. idle, prepare — internal use
  4. poll — retrieve new I/O events; may block here
  5. check — setImmediate callbacks
  6. close callbacks — e.g. socket.on('close')

Microtasks vs macrotasks

  • Microtasks (between every phase): Promise callbacks (.then, await), queueMicrotask
  • nextTick queue (highest priority): process.nextTick — runs before other microtasks; can starve I/O if abused
  • Macrotasks: timers, I/O, setImmediate
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
process.nextTick(() => console.log('4'));
// Output: 1, 4, 3, 2

Blocking the loop

Synchronous CPU work (JSON.parse of huge files, bcrypt rounds, tight loops) delays all I/O. Monitor with perf_hooks or event-loop-lag npm package.

EventEmitter

Node's pub/sub pattern. Core classes (Stream, net.Server, process) extend EventEmitter.

const EventEmitter = require('events');
class OrderService extends EventEmitter {
  placeOrder(order) {
    this.emit('order:placed', order);
  }
}
const svc = new OrderService();
svc.on('order:placed', (o) => console.log(o));
svc.setMaxListeners(20); // avoid MaxListenersExceededWarning in large apps
  • once — auto-remove after first fire
  • error event — if unhandled and no listener, process crashes
  • EventEmitter.asyncIterator — consume events with for await

Buffers

Fixed-size raw memory for binary data. Buffer is a subclass of Uint8Array.

const buf = Buffer.from('hello', 'utf8');
buf.toString('base64');
Buffer.alloc(1024);       // zero-filled (safe)
Buffer.allocUnsafe(1024); // faster, may contain old data
  • Use Buffers for TCP streams, file chunks, crypto operations.
  • Buffer.concat([buf1, buf2]) — combine chunks from streams.
  • Prefer TextEncoder/TextDecoder for string/binary in modern code.

Streams

Process data chunk-by-chunk instead of loading everything into memory.

Types

  • Readable — source (fs.createReadStream, HTTP request body)
  • Writable — sink (fs.createWriteStream, HTTP response)
  • Duplex — both (TCP socket)
  • Transform — modify data in transit (zlib.createGzip)

Backpressure

writable.write(chunk);
// if write() returns false, pause readable until 'drain'
readable.on('data', (chunk) => {
  if (!writable.write(chunk)) readable.pause();
});
writable.on('drain', () => readable.resume());

// Or use pipeline (handles errors + backpressure)
const { pipeline } = require('stream/promises');
await pipeline(readable, transform, writable);

Object mode

Streams can carry JS objects instead of Buffers ({ objectMode: true }) — useful for parsing pipelines.

HTTP

import http from 'node:http';
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ ok: true }));
});
server.listen(3000);
  • http.Agent — connection pooling for outbound requests (keepAlive: true)
  • node:http2 — multiplexing, server push (rarely used in Node APIs)
  • Prefer fetch (Node 18+) or undici for client requests
  • Always set timeouts: server.requestTimeout, server.headersTimeout

Express / Middleware

Express is a minimal web framework. Everything is middleware — functions with signature (req, res, next).

app.use(express.json({ limit: '1mb' }));
app.use('/api', authMiddleware);

app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await userService.find(req.params.id);
    if (!user) return res.status(404).json({ error: 'Not found' });
    res.json(user);
  } catch (err) { next(err); }
});

// Error middleware — 4 args, must be last
app.use((err, req, res, next) => {
  logger.error(err);
  res.status(err.status || 500).json({ error: err.message });
});

Middleware order matters

  1. Security (helmet, cors, rate limiter)
  2. Body parsers
  3. Authentication
  4. Routes
  5. 404 handler
  6. Error handler

Alternatives

Fastify (schema validation, faster), Koa (async middleware via ctx), Hono (edge/lightweight), NestJS (opinionated, DI, decorators).

REST

Design principles

  • Resources as nouns: /users, /orders/{id}
  • HTTP verbs: GET (read), POST (create), PUT (replace), PATCH (partial), DELETE
  • Status codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests, 500 Internal Error
  • Idempotency: GET, PUT, DELETE are idempotent; POST is not

Pagination

GET /users?cursor=abc123&limit=20
// Response: { data: [...], nextCursor: "def456", hasMore: true }

HATEOAS (optional at senior level)

Include links in responses: { "id": 1, "_links": { "self": "/users/1", "orders": "/users/1/orders" } }

Validation

Validate at the boundary — never trust client input.

// Zod example
const CreateUser = z.object({
  email: z.string().email(),
  age: z.number().int().min(18),
});
const parsed = CreateUser.safeParse(req.body);
if (!parsed.success) return res.status(422).json(parsed.error.flatten());
  • Zod — TypeScript-first, infer types from schemas
  • Joi — mature, widely used in Express apps
  • class-validator — NestJS decorator-based
  • Validate params, query, body, and headers separately
  • Sanitize strings (trim, escape HTML) before storage

Error Handling

Operational vs programmer errors

  • Operational — expected failures (404, validation, network timeout). Handle gracefully.
  • Programmer — bugs (TypeError, null reference). Log, alert, possibly crash process.
class AppError extends Error {
  constructor(message, status = 500, code = 'INTERNAL') {
    super(message);
    this.status = status;
    this.code = code;
    this.isOperational = true;
  }
}
  • Centralized error middleware in Express
  • Never expose stack traces in production responses
  • process.on('uncaughtException') — log and graceful shutdown (don't continue serving)
  • Correlation IDs in logs to trace requests across services

Auth

Session-based

  • Server stores session (Redis/DB); client gets session cookie (httpOnly, secure, sameSite)
  • Good for traditional web apps, easy revocation

JWT (stateless)

  • Access token (short-lived, 15 min) + refresh token (long-lived, stored securely)
  • Payload: { sub, roles, iat, exp } — don't store sensitive data (JWT is base64, not encrypted)
  • Verify signature on every request; rotate refresh tokens

Password storage

const hash = await bcrypt.hash(password, 12); // cost factor 10-12
const valid = await bcrypt.compare(password, hash);

OAuth 2.0 / OIDC

Delegate auth to providers (Google, GitHub). Use Passport.js or openid-client. Authorization Code flow with PKCE for SPAs.

RBAC / ABAC

Role-based (admin, editor) or attribute-based (owner of resource). Check permissions in middleware, not just authentication.

SQL / Transactions / Prisma

Core concepts

  • Indexes — B-tree default; composite index column order matters
  • Transactions — ACID; use for multi-step writes that must succeed or fail together
  • Isolation levels — Read Committed (default PG), Repeatable Read, Serializable
  • N+1 problem — fix with JOINs or eager loading (include in Prisma)
// Prisma transaction
await prisma.$transaction(async (tx) => {
  const account = await tx.account.update({
    where: { id: fromId },
    data: { balance: { decrement: amount } },
  });
  await tx.account.update({
    where: { id: toId },
    data: { balance: { increment: amount } },
  });
});

Connection pooling

Use PgBouncer or Prisma Accelerate in serverless. Set pool size based on: connections = (core_count * 2) + effective_spindle_count — don't exceed DB max connections.

MongoDB vs SQL

AspectSQL (PostgreSQL)MongoDB
Data modelRelational, normalized tablesDocument (BSON), flexible schema
SchemaStrict, migrations requiredSchema-less (but enforce in app or JSON Schema)
JoinsNative JOINs, powerful queries$lookup ( slower than SQL joins )
TransactionsMature, ACID defaultMulti-doc ACID since 4.0 (replica set required)
ScalingVertical + read replicas; sharding harderHorizontal sharding built-in
Best forComplex relations, reporting, financial dataRapid iteration, nested documents, high write throughput

When to use SQL

  • Complex queries with multiple joins and aggregations
  • Strong consistency requirements (banking, inventory)
  • Well-defined schema that rarely changes
  • Need for foreign keys, constraints, and referential integrity

When to use MongoDB

  • Document structure maps naturally to app objects (CMS, catalogs, IoT events)
  • Schema evolves frequently during early product stages
  • Horizontal scaling with sharding is a primary requirement
  • Geospatial queries, text search (Atlas Search)

Polyglot persistence

Many systems use PostgreSQL for transactional core + MongoDB/Elasticsearch for search/logs. Don't pick one database for everything.

Redis / Caching

Patterns

  • Cache-aside — app checks cache → miss → read DB → write cache
  • Write-through — write to cache and DB simultaneously
  • Write-behind — write cache first, async flush to DB (risk of data loss)
async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);
  const user = await db.users.find(id);
  await redis.setex(`user:${id}`, 3600, JSON.stringify(user));
  return user;
}

Redis data structures

  • Strings — simple KV cache
  • Hashes — object fields
  • Sorted sets — leaderboards
  • Pub/Sub — lightweight messaging (no persistence)
  • Streams — persistent event log (lighter Kafka alternative)

Cache invalidation

Hardest problem in CS. Strategies: TTL expiry, event-driven invalidation (on write), versioned keys (user:123:v2).

Security

  • Helmet — sets security HTTP headers (CSP, HSTS, X-Frame-Options)
  • CORS — whitelist origins; never * with credentials
  • Rate limiting — express-rate-limit + Redis store for distributed apps
  • Input validation — Zod/Joi at every entry point
  • SQL injection — parameterized queries only (Prisma/ORM handles this)
  • Secrets — env vars or vault; never commit .env
  • Dependencies — npm audit, Dependabot, lock files
  • CSRF — tokens for cookie-based auth; less relevant for JWT in Authorization header

Testing / Logging

Testing pyramid

  • Unit — Jest/Vitest, mock dependencies, fast
  • Integration — supertest for HTTP, testcontainers for real DB/Redis
  • E2E — full stack with Docker Compose
// supertest example
const res = await request(app).get('/api/users').set('Authorization', `Bearer ${token}`);
expect(res.status).toBe(200);

Logging

  • Structured logging — pino or winston with JSON output
  • Include: timestamp, level, requestId, userId, service name
  • Log levels: error (action needed), warn (investigate), info (business events), debug (dev only)
  • Ship logs to ELK, Datadog, or CloudWatch — don't rely on stdout alone in production

Workers / Cluster

Cluster module

const cluster = require('cluster');
const os = require('os');
if (cluster.isPrimary) {
  for (let i = 0; i < os.cpus().length; i++) cluster.fork();
  cluster.on('exit', (worker) => cluster.fork()); // auto-restart
} else {
  require('./server'); // each worker runs the HTTP server
}

Forks processes — shared nothing. Good for I/O-bound HTTP servers. OS distributes connections.

Worker Threads

const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');
if (isMainThread) {
  new Worker(__filename, { workerData: { n: 40 } });
} else {
  const result = fibonacci(workerData.n);
  parentPort.postMessage(result);
}

Shared memory possible via SharedArrayBuffer. Use for CPU-bound tasks (image processing, PDF generation, heavy computation).

ClusterWorker Threads
UnitProcess (separate memory)Thread (can share memory)
Best forI/O-bound HTTP serversCPU-bound computation
OverheadHigher (full process)Lower (shared process)
Crash isolationOne worker crash ≠ all downUnhandled error can crash process

Queues / Kafka / WebSockets / GraphQL / Rate Limiting

Message queues

  • Bull/BullMQ — Redis-backed job queues for Node (email, reports, retries)
  • AWS SQS — managed, at-least-once delivery, visibility timeout
  • RabbitMQ — AMQP, routing, dead-letter exchanges

Apache Kafka

  • Distributed commit log — topics partitioned across brokers
  • Consumer groups — each partition consumed by one consumer in group
  • Use for: event sourcing, log aggregation, stream processing, decoupling microservices
  • Node client: kafkajs — handle rebalances, idempotent producers

WebSockets

const { WebSocketServer } = require('ws');
const wss = new WebSocketServer({ server });
wss.on('connection', (ws) => {
  ws.on('message', (data) => ws.send(`echo: ${data}`));
});

Full-duplex, persistent connection. Use for chat, live dashboards, collaborative editing. Consider SSE for server→client only (simpler, works through HTTP proxies).

GraphQL

  • Single endpoint, client specifies shape of response
  • N+1 problem — solve with DataLoader (batch + cache per request)
  • Apollo Server or Mercurius (Fastify) for Node
  • Complexity limiting to prevent expensive queries

Rate limiting

  • Token bucket — tokens refill at fixed rate; burst allowed
  • Sliding window — count requests in rolling time window
  • Implement at API gateway (Nginx, Kong) or app layer (express-rate-limit + Redis)
  • Return 429 with Retry-After header

gRPC vs REST

AspectRESTgRPC
ProtocolHTTP/1.1 or HTTP/2, JSONHTTP/2, Protocol Buffers (binary)
ContractOpenAPI/Swagger (optional).proto files (required, strict)
PerformanceHuman-readable, larger payloadsSmaller payloads, faster serialization
StreamingSSE, WebSockets (separate)Built-in bidirectional streaming

When to choose gRPC

  • Service-to-service communication inside a cluster
  • High throughput, low latency requirements
  • Strong typing and code generation from .proto schemas
  • Bidirectional streaming (real-time feeds between services)

When to choose REST

  • Public-facing APIs consumed by browsers and third parties
  • Simple CRUD with wide tooling support
  • Team familiarity and faster iteration without schema compilation

Performance

  • Don't block the event loop — profile with clinic.js (doctor, bubbleprof, flame)
  • Connection pooling — DB, Redis, HTTP keep-alive
  • Streaming — never read entire files into memory
  • Caching — Redis for hot data, CDN for static assets
  • Compression — gzip/brotli middleware for responses
  • Cluster/workers — utilize all CPU cores
  • Lazy loading — dynamic imports for heavy modules
  • Memory leaks — watch for growing closures, unremoved listeners, global caches without TTL
  • JSON — consider flat buffers or protobuf for high-throughput internal APIs

Nginx Reverse Proxy

Nginx sits in front of Node.js apps handling SSL, load balancing, static files, and rate limiting.

upstream node_app {
    least_conn;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;

    location / {
        proxy_pass http://node_app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /static/ {
        alias /var/www/static/;
        expires 30d;
    }
}

Why use Nginx

  • SSL/TLS termination — Node doesn't handle certs
  • Load balancing across cluster workers or multiple instances
  • Serve static assets efficiently (bypass Node entirely)
  • Rate limiting, request buffering, gzip compression
  • WebSocket proxy support

Kubernetes Basics

Kubernetes (K8s) orchestrates containers at scale — beyond what Docker Compose offers.

Core objects

  • Pod — smallest deployable unit; one or more containers sharing network/storage
  • Deployment — declarative desired state for pods (replicas, rolling updates, rollbacks)
  • Service — stable network endpoint (ClusterIP internal, LoadBalancer external)
  • ConfigMap / Secret — inject config and credentials as env vars or files
  • Ingress — HTTP routing rules (like Nginx config, often backed by Nginx/Traefik controller)
  • HPA — Horizontal Pod Autoscaler scales replicas based on CPU/memory/custom metrics
apiVersion: apps/v1
kind: Deployment
metadata:
  name: node-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: node-api
  template:
    metadata:
      labels:
        app: node-api
    spec:
      containers:
      - name: api
        image: myregistry/node-api:1.2.0
        ports:
        - containerPort: 3000
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"

OpenAPI / Swagger

OpenAPI Specification (OAS) defines REST API contracts in YAML/JSON. Swagger is the tooling ecosystem (UI, codegen, validator).

openapi: 3.0.3
info:
  title: User API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: User found
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'

Benefits

  • Contract-first — design API before implementation
  • Swagger UI — interactive docs at /api-docs
  • Code generation — client SDKs, server stubs
  • Validation — express-openapi-validator middleware
  • Testing — contract tests ensure implementation matches spec

12-Factor App Principles

  1. Codebase — one repo per app (monorepo ok if one deployable unit)
  2. Dependencies — explicitly declare (package.json); never rely on system packages
  3. Config — store in environment variables, not code
  4. Backing services — treat DB, Redis, queues as attached resources (swappable via URL)
  5. Build, release, run — strict separation; immutable releases
  6. Processes — stateless, share-nothing; state in backing services
  7. Port binding — self-contained HTTP server (Node exports port)
  8. Concurrency — scale via process model (cluster, K8s replicas)
  9. Disposability — fast startup, graceful shutdown (SIGTERM handler)
  10. Dev/prod parity — minimize gaps (Docker helps)
  11. Logs — treat as event streams (stdout), don't manage log files
  12. Admin processes — one-off tasks (migrations) as separate processes, not baked into server
// Graceful shutdown (Factor 9)
process.on('SIGTERM', async () => {
  server.close(() => process.exit(0));
  await prisma.$disconnect();
  setTimeout(() => process.exit(1), 10000); // force exit after 10s
});

API Versioning Strategies

URL path versioning

GET /api/v1/users
GET /api/v2/users

Most common, explicit, easy to route. Downside: URL pollution, maintaining multiple code paths.

Header versioning

GET /api/users
Accept: application/vnd.myapp.v2+json

Clean URLs. Harder to test in browser, less visible.

Query parameter

GET /api/users?version=2

Simple but often feels like an afterthought.

Best practices

  • Version only when making breaking changes (remove field, change type, rename endpoint)
  • Adding optional fields is NOT breaking — no version bump needed
  • Support N-1 version during migration period; deprecate with Sunset header
  • Document changes in changelog; use OpenAPI diff tools
  • Consider feature flags for gradual rollout instead of full version fork

Distributed Systems

Challenges

Network partitions, partial failures, clock skew, consistency vs availability (CAP). Design for failure — every remote call can fail.

Saga pattern

Manage distributed transactions as a sequence of local transactions with compensating actions.

  • Choreography — services react to events (OrderCreated → PaymentProcessed → Shipped)
  • Orchestration — central coordinator directs each step
  • Compensating transaction: if shipping fails, refund payment

Transactional Outbox

Write business data + outbox event in the same DB transaction. Separate relay process publishes events to Kafka/RabbitMQ. Guarantees at-least-once delivery without dual-write problem.

await prisma.$transaction([
  prisma.order.create({ data: order }),
  prisma.outbox.create({ data: { event: 'OrderCreated', payload: order } }),
]);
// Relay worker polls outbox → publishes to queue → marks as sent

CQRS (Command Query Responsibility Segregation)

  • Command side — handles writes, validates business rules
  • Query side — optimized read models (denormalized, materialized views)
  • Eventual consistency between write and read models
  • Use when read/write patterns differ significantly (heavy reads, complex writes)

Event Sourcing

Store state changes as immutable event log instead of current state. Rebuild state by replaying events. Pairs naturally with CQRS and Kafka.

Circuit breaker

Stop calling a failing service after threshold. States: closed (normal) → open (fail fast) → half-open (test recovery). Libraries: opossum.

Other patterns

  • API Gateway — single entry point, auth, routing, rate limiting
  • Service mesh — Istio/Linkerd for mTLS, observability, retries between pods
  • Strangler fig — gradually replace monolith by routing traffic to new services
  • Bulkhead — isolate failures (separate thread pools / connection limits per dependency)
